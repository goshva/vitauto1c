## Последние две группы

**Заказы покупателя (5).** У заказа **нет собственного статуса** — он выводится из строк.
Заказ это папка для строк, и его «статус» всегда «самая отстающая строка». Отдельное
поле пришлось бы синхронизировать со строками, и оно неизбежно разошлось бы.

Свод по заказу считается **на сервере**: если считать на клиенте, карточка заказа и
список строк начнут показывать разные суммы.

**Строки (6).** Свод по статусам, массовая правка поля, удаление, восстановление,
массовое удаление, выгрузка CSV.

Массовые операции работают **только по отмеченным** строкам: «выделить всё» нет
намеренно — в legacy оно на 154 строках приводило к массовым ошибкам.

## Что проверяют тесты, кроме кодов ответов

| Проверка | Что доказывает |
|---|---|
| `GET /lines/summary` отвечает 200, а не 400 | порядок монтирования: свод не перехвачен `/lines/{id}` с проверкой UUID |
| после массовой правки отметки сняты | следующее действие не заденет те же строки незаметно |
| массово правится только разрешённый список полей | `quantity`, `sale_price`, `status` отвергаются |
| CSV начинается с BOM и разделён точкой с запятой | без BOM Excel в русской локали ломает кириллицу |
| `Фильтр; "масляный"` → `"Фильтр; ""масляный"""` | экранирование CSV, а не «файл открылся» |
| отгруженную строку удалить нельзя, текст перечисляет статусы | сообщение ведёт оператора, а не сообщает «нельзя» |

## Дефект, который сборка не поймала

При разделении `lines-bulk.ts` константа `DELETABLE` осталась в первом файле.
**Bun собрал оба файла без ошибок** — проверки типов нет, `DELETABLE` стал бы
`ReferenceError` только в рантайме. Поймано при чтении результата разделения,
а не сборкой.

Это ограничение выбранного инструмента: `bun build` транспилирует, но не проверяет
типы. В этапе 6 стоит добавить `tsc --noEmit` в гейт.
