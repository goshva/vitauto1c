# Резервные копии: как снимать и как восстанавливать

**Проверено 15.11.2026:** полный цикл «снять → проверить → восстановить» пройден,
16 тестов на копии зелёные.

---

## Три команды

```bash
# 1. Снять копию (в backups/, хранить 7 последних)
bun run backup

# 2. Проверить её ВОССТАНОВЛЕНИЕМ — обязательный шаг
bun run backup:verify

# 3. Восстановить (в день аварии)
bun run backup:restore 20261115-162203 --to vitauto_proto
```

---

## Главное правило

**Копия, которую ни разу не восстанавливали, копией не является.**

Файл может быть усечён, опись — устареть, восстановление — упереться в отсутствующее
расширение. Узнать об этом лучше сейчас, чем в день аварии. Поэтому `backup:verify`
не смотрит на файл — она **восстанавливает его в отдельную базу и сверяет содержимое**.

## Что именно считается доказательством

Копия снимается **вместе с описью**: слепок содержимого каждой таблицы на момент
снятия.

| Что проверяется | Что это ловит |
|---|---|
| Контрольная сумма файла | копию подменили или усекли |
| Восстановление в **чужую** базу | дамп нечитаем, расширения не те |
| Слепок содержимого | пропавшие и изменённые строки |

**Размер файла ничего не доказывает.** Дамп может быть усечён и при этом весить
правдоподобно. **Число таблиц — тоже**: оно не меняется.

Слепок снимается **с базы в момент копии**, а не с копии: сравнение копии с самой
собой сходится всегда — это и есть та проверка, которая ничего не проверяет.

**Проверка ловит плохую копию — это проверено тестом.** Есть три проверки: обрезанный
файл, подменённый файл того же размера, и полный цикл с испорченным дампом. Каждая
обязана отказать.

## Что НЕ покрыто — сказать прямо

| Не покрыто | Чем это грозит |
|---|---|
| **Копии лежат на той же машине, что и база** | **потеря диска уничтожит и базу, и копии** |
| Нет копирования на внешний носитель | то же |
| Нет точки восстановления на момент времени (PITR) | потеряются правки после последней копии |
| Нет проверки по расписанию | копия, снятая вчера, могла испортиться и никто не узнает |
| Не сохраняется `SESSION_SECRET` | после восстановления на новой машине у всех слетят сессии (не страшно, но знать надо) |

**Копии на том же диске спасают от порчи данных и от ошибочной правки, но не от
потери диска.** Это осознанное ограничение объёма, а не недосмотр.

## Расписание

Пока не настроено — это отдельный пункт («регламентные задания»). До тех пор копии
снимаются **вручную**, и это надо помнить.

Когда будет настроено — предлагаемый порядок:

| Когда | Что |
|---|---|
| Ежедневно, вечером | `bun run backup` |
| Еженедельно, в выходной | `bun run backup:verify` — полная проверка восстановлением |
| Перед обновлением | `bun run backup --keep 30` — с запасом, чтобы было к чему вернуться |
| Перед приёмкой | `bun run backup && bun run backup:verify` |

Ежедневная копия занимает **около минуты** (база 15 МБ, дамп 0.1 МБ). Еженедельная
проверка — **около десяти секунд**.

Задача Windows для ежедневного снятия:

```powershell
schtasks /create /tn "Vitauto backup" /sc daily /st 20:00 /tr ^
  "cmd /c cd /d C:\Bases1C\vitauto1c\proto && bun run backup >> logs\backup.log 2>&1"
```

## День аварии: порядок действий

1. **Остановить приложение** (`Ctrl+C` в окне сервера). Иначе восстановление будет
   писать в базу, из которой в этот момент читают.

2. **Посмотреть, какие копии есть:**
   ```bash
   dir backups
   ```
   Имя — время снятия: `vitauto-20261115-162203.dump`.

3. **Проверить выбранную копию ДО восстановления:**
   ```bash
   bun run backup:verify 20261115-162203
   ```
   Если она не годится — взять следующую. Восстанавливать из непроверенной копии
   хуже, чем не восстанавливать: получится база, которая **выглядит** рабочей, но в
   ней не хватает строк.

4. **Восстановить:**
   ```bash
   bun run backup:restore 20261115-162203 --to vitauto_proto
   ```
   Целевую базу надо назвать **явно**. Команда, которая по умолчанию бьёт в рабочую
   базу, — это команда, которую однажды запустят по ошибке, и восстанавливать будет
   уже нечего.

5. **Запустить приложение и проверить глазами:** открыть список строк, найти заказ,
   посмотреть остаток. Данные должны быть на момент снятия копии — правки после неё
   потеряны.

6. **Применить миграции**, если копия снята до обновления схемы:
   ```bash
   bun run db:migrate
   ```

## Восстановление «на посмотреть», не ломая рабочую базу

Иногда копию надо открыть, а не восстановить. Тогда — в отдельную базу:

```bash
bun run backup:restore 20261115-162203 --to vitauto_inspect --create
```

`--create` создаёт целевую базу заново. Посмотреть её можно, подставив адрес:

```bash
DATABASE_URL=postgres://postgres:postgres@127.0.0.1:5434/vitauto_inspect bun run start
```

## Почему копии не попадают в репозиторий

`.gitignore` исключает `backups/` и `*.dump`. Дамп содержит **себестоимость, цены
закупки и данные клиентов** — попади он в репозиторий, закрытые колонки (ФТ v2 п. 5)
стали бы доступны любому, у кого есть доступ к коду. К тому же копии весят десятки
мегабайт и меняются каждый раз: история репозитория распухла бы.
