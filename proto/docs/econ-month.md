# Экономика месяца: расчёт, прогон действиями и обоснование оплаты

**Дата:** 18.11.2026 · **Стенд:** `vitauto_proto` (127.0.0.1:5434) · **Задание:** зарплата
100 000 ₽ на роль + 25% от услуг исполнителю

Отчёт отвечает на один вопрос: **сколько сервис заработал за месяц и покрывает ли эта
прибыль объявленную оплату труда**. Месяц считается ДВАЖДЫ — предварительно, из входных
значений, и по факту, после того как сотрудники прошли процессы через API. Совпадение
двух чисел и есть проверка расчёта.

---

## 1. Как это устроено

| Файл | Что делает |
|---|---|
| `src/domain/econ.ts` | условия оплаты, итоги (`summarize`), фонд (`payroll`) |
| `src/domain/econ-plan.ts` | синтетический план месяца: количества, закупка, множители, нормо-часы |
| `src/domain/econ-roles.ts` | отнесение прибыли на роли по участию в узлах процесса |
| `db/seed-econ.ts` | сид: справочники + чистое состояние + входные значения месяца |
| `scripts/econ-run.ts` | прогон по узлам карты процессов (`db/process-map.json`) |
| `scripts/econ-nodes.ts` | соответствие «узел карты → адрес приложения» |
| `scripts/econ-actions.ts` | действия сотрудников: вставка листа, приёмка, отгрузка, работы |
| `scripts/econ-actual.ts` | факт из базы: продажа по правилу отчёта + закрытые наряды |
| `scripts/econ-month.ts` | сборка: сид → расчёт → прогон → факт → сверка → отчёт |
| `tests/integration/econ-month.test.ts` | 11 проверок: арифметика, сверка, документы, оплата |

**Сид не создаёт проводки.** Он готовит справочники, чистит транзакции и отдаёт входные
значения. Заказы, приёмки, отгрузки и работы появляются только действиями: если бы сид
клал готовые суммы, «план» и «факт» сверялись бы с одним источником и сверка не
проверяла бы ничего.

**Действия идут по узлам карты процессов.** Прогон читает `db/process-map.json` и на
каждом шаге вызывает адрес, закреплённый за узлом. Порядок узлов — из карты, поэтому её
изменение меняет прогон, а не только подпись на экране.

## 2. Месяц: входные значения

```json
{"happyLines":60,"stockLines":40,"workOrders":50,"laborPerOrder":2,"partsPerOrder":1,"seed":20261118}
```

| Канал | Объектов | Что это |
|---|---|---|
| `happy` | 60 строк | закупка под заказ: заявка → заказ → оплата → приёмка → комплектация → отгрузка |
| `stock` | 40 строк | со склада: резерв → комплектация → отгрузка (без закупки) |
| `car_repair_in` | 50 нарядов | ремонт: наряд → запчасти → приёмка → работы механика → закрытие |

Итого **250 строк** (150 запчастей + 100 работ) и **50 заказ-нарядов** — примерно
7 заказов в день при 22 рабочих днях. Цены — из справочника номенклатуры, множитель
1,30–1,65, нормо-час 1500 ₽.

каждой строке продажи, строки наряда получили процесс при создании.

## 4. Действия по ролям и средние значения

Прогон: **2410 узлов**, из них **1640 с адресом**, **3380 HTTP-запросов**, **0 отказов**.

| Роль | Узлов | Запросов | Записей журнала | Вклад, ₽ | Выплата, ₽ | Покрытие |
|---|---:|---:|---:|---:|---:|---:|
| Менеджер | 1740 | 1170 | 890 | 286 799,04 | 100 000,00 | **287%** |
| Механик | 200 | 150 | **200** | 130 959,88 | 225 126,25 | 58% |
| Кладовщик | 470 | 320 | 220 | 125 211,19 | 100 000,00 | **125%** |
| Поставщик (внешний) | 0 | 0 | 0 | 73 328,73 | — | — |
| Клиент (внешний) | 0 | 0 | 0 | 48 053,96 | — | — |

«Вклад» — прибыль и услуги, отнесённые на роль по участию в узлах её процессов;
«выплата» — оклад плюс доля исполнителя. **Это разные величины**: доля считается от
выручки за услуги, а не от вклада, поэтому у механика выплата растёт вместе с услугами.

«Узлов» — сколько узлов карты выполнил сотрудник этой роли. Оно больше числа узлов,
принадлежащих роли по карте: узлы клиента (N1, N2a) и поставщика (P1, P2) тоже нажимает
менеджер, потому что учётных записей у внешних сторон нет. Поэтому 1740 узлов менеджера
против 1170 узлов, отнесённых на роль «менеджер» в развесовке прибыли.

Средние значения месяца:

| Показатель | Значение |
|---|---:|
| Заказов в день (22 рабочих дня) | 6,8 |
| Средний чек заказ-наряда | 13 404,29 ₽ (от 5 013,00 до 25 492,50) |
| Средняя строка продажи | 3 328,73 ₽, прибыль 1 077,73 ₽ (32,4%) |
| Средняя работа | 3,34 нормо-часа, 5 005,05 ₽ |
| Наценка на запчасти | 32,6% к себестоимости |
| Узлов на роль в день | менеджер 79, кладовщик 21, механик 9 |
| Вклад одного узла | менеджер 165 ₽, кладовщик 266 ₽, механик 655 ₽ |

**Отнесение по узлам смещено в пользу менеджера, и это свойство карты, а не оценка
пользы роли:** из 131 шага модели 70 принадлежат менеджеру. Поэтому рядом стоит вторая
величина для механика — доля исполнителя, считающаяся от денег, а не от числа шагов.

## 5. Обоснование оплаты

| Условие | Сумма |
|---|---:|
| Оклады: 5 ролей × 100 000 ₽ | 500 000,00 |
| Доля исполнителя: 25% × 500 505,00 ₽ | 125 126,25 |
| **Фонд оплаты** | **625 126,25** |
| Прибыль до фонда | 664 352,80 |
| **Покрытие** | **106,3%** |
| Чистый результат | +39 226,55 |
| Заказов в месяце | 150 |
| Для окупаемости нужно | **142** |

Вывод по ролям:

- **Менеджер — 287%**: роль, которая ведёт заявку, цены, закупку, комплектацию и
  закрытие; вклад покрывает оклад почти втрое.
- **Кладовщик — 125%**: покрывает оклад, но запаса мало — при падении объёма на 20%
  роль уходит в минус (470 узлов и 220 записей журнала — самые «ручные» операции).
- **Механик — 58% по узлам, но услуги прибыльны**: доля 25% (125 126,25 ₽) плюс оклад
  (100 000 ₽) против вклада 130 959,88 ₽. Если смотреть на услуги как на поток:
  500 505,00 − 125 126,25 = **375 378,75 ₽ остаётся в общем котле**, то есть услуги
  окупают и долю, и оклад механика, и дают 275 378,75 ₽ сверх.
- **Администратор и муниципалитет** в этом месяце действий не выполняли (0 узлов), но
  оклады учтены: 200 000 ₽ из 500 000 ₽ фонда приходятся на роли, которых месячная
  розничная работа не загружает. Это надо назвать прямо: **роль «муниципалитет» должна
  окупаться тендерами, а не розницей**, иначе 100 000 ₽ ей обосновать нечем.

**Чего расчёт не учитывает, и это меняет вывод.** Считаны только прямые затраты: материалы,
доля исполнителя и оклады. Нет страховых взносов, аренды, налогов, амортизации и
накладных. Со взносами 30% на фонд оплаты картина другая:

| Со взносами 30% | Сумма |
|---|---:|
| Фонд оплаты | 625 126,25 |
| Взносы (30%) | 187 537,88 |
| **Итого на оплату труда** | **812 664,13** |
| Прибыль до фонда | 664 352,80 |
| **Покрытие** | **81,8%** |
| Чистый результат | **−148 311,33** |
| Для окупаемости нужно | **184 заказа** (вместо 142) |

То есть **объявленные условия окупаются только при 184 заказах в месяц** (8,4 в день), а
не при 150. При 150 заказах без взносов запас 39 226,55 ₽ — это 5,9% прибыли, то есть
подтверждение «впритык», а не устойчивая модель.

## 6. Что проверено тестами

`bun test tests/integration/econ-month.test.ts` — **11 проверок, все зелёные**:

| Проверка | Что доказывает |
|---|---|
| цена продажи = закупка × множитель | правило цены совпадает с сервером |
| прибыль = выручка − себестоимость, услуги по нормо-часам | арифметика условия |
| фонд = 5 окладов + 25% услуг | условия оплаты не «примерно», а точно |
| вклад ролей сходится с прибылью целиком | ни рубля не потеряно и не выдумано |
| все узлы пройдены без отказов | прогон доходит до конца по карте |
| факт совпадает с планом до копейки | сверка двух независимых расчётов |
| приёмки проведены, отгрузки отгружены, наряды закрыты | деньги подтверждены документами |
| журнал подтверждает работу ролей | независимая мера действий |
| выручка ремонта не попадает в отчёт о прибыли | находка §7.1 |
| сжатый месяц не окупается | фонд виден числом, а не словами |
| окупаемость от вклада одного заказа | «нужно N» — проверяемое условие |

## 7. Что прогон вскрыл (находки)

**Все четыре находки исправлены 19.11.2026** — порядок правок и проверки в
`docs/fix-plan.md`. Ниже они оставлены с пометкой «исправлено», потому что именно этот
прогон их и обнаружил: расчёт сошёлся до копейки, а дефекты нашлись рядом с числами.

1. **Отчёт о прибыли не видит ремонт.** `src/reports-data.ts:30-56` требует дату
   отгрузки, а у заказ-наряда её нет: ремонт выполняется, а не отгружается. Отчёт
   показывает **332 873,30 ₽** выручки, тогда как фактическая выручка месяца —
   **1 003 087,80 ₽**. Мимо отчёта проходят все работы (500 505,00 ₽) и запчасти
   ремонта (169 709,50 ₽) — **670 214,50 ₽, две трети оборота**.
   **Исправлено 19–20.11.2026:** у наряда появилась дата признания
   `work_order.closed_at` (миграция `0031_long_hellfire_club.sql`), а ремонт получил
   **ОТДЕЛЬНЫЙ отчёт** `/reports/repair` (вкладка «Ремонт») — решение заказчика
   20.11.2026. Теперь два отчёта вместе дают выручку месяца: продажи **332 873,30 ₽**
   плюс ремонт **670 214,50 ₽** = **1 003 087,80 ₽**, и это проверяется тестом.
2. **Работы механика не попадают в журнал.** `work-orders-flow.ts` (добавление работы),
   `work-orders-parts.ts` и `work-orders-status.ts` не вызывают `record` — при 200
   узлах механика в журнале **0 записей**. Сдельная выработка считается по строкам, но
   «кто выполнил работу» в журнале не отражено.
   **Исправлено:** все три пути пишут в журнал (`entity: 'work_order'`, исполнитель —
   в `details`). В новом прогоне у механика **200 записей** вместо нуля
   (`docs/fix-plan.md` §2).
3. **Ремонт: сценарий карты противоречил её же графу.** Карта вела запчасти в «резерв»
   (M3), а задание забирало строки только из `new / in_work / ready_to_ship`
   (`src/operations.ts:17`) — «заказан» из резерва недостижим. Причина была в модели:
   сценарий `car_repair_in` ставил M3 перед M4, а таблица переходов той же модели
   `reserve → ordered` не содержит.
   **Исправлено 20.11.2026 по решению заказчика:** «зарезервировали, не хватило —
   заказали» — это РЕАЛЬНЫЙ процесс, поэтому шаг M3 возвращён, в модель добавлен переход
   `reserve → ordered`, а `JOB_FROM` принимает строки из «Резерва». Дополнительно
   добавлен сценарий **«ремонт со склада»** (`repair_stock`, 10 шагов): запчасть есть,
   закупка не нужна. Процессов стало **12**, шагов **131**.
   **Поправка к первой редакции отчёта (19.11.2026):** расхождения карты и кода в
   отгрузке нет. По модели `M12` — «Отгрузочная ведомость», `K5` — «Отгрузка клиенту»,
   то есть карта права, а перепутаны были **метки узлов в комментариях кода**
   (`src/shipments.ts:12`). Исправлено, см. `docs/fix-plan.md` §3.2.
4. **API не ставит строку в процесс.** `process_id` / `process_step` только читаются
   (`src/lines-steps.ts`, `src/lines-ui.ts`) и заполняются лишь сидами процессов. Строка,
   созданная через API, в процессе не числится, и пошаговое движение `/lines/step` для
   неё недоступно — прогон вёл её переходами состояний и документами.
   **Исправлено:** появился адрес `POST /lines/{id}/process` с отдельным правом
   `process.assign`, строки наряда получают процесс при создании, а прогон месяца
   назначает сценарий каждой строке продажи. В новом прогоне **все 250 строк стоят в
   процессе** (`docs/fix-plan.md` §4).
5. **Отметка «документ подписан оригинал» обязательна, но ставится вручную.** Без неё
   закрытие отгруженной строки отклоняется (C22) — прогон выяснил это отказом 409 на
   первом запуске, а не чтением кода.
6. **Приёмка создаёт движение только при проведении.** 110 приёмок → 110 движений
   прихода; отдельного резерва как движения склада нет, поэтому «со склада» в модели
   отличается от «под заказ» только отсутствием закупки.

## 8. Как воспроизвести

```powershell
cd C:\Bases1C\vitauto1c\proto
bun run scripts/econ-month.ts            # полный месяц (250 строк, ~3200 запросов)
bun run scripts/econ-month.ts small      # сжатый месяц для проверки
bun run scripts/econ-month.ts --seed 7   # другой синтетический набор
bun test tests/integration/econ-month.test.ts
```

Отчёт прогона пишется в `logs/econ-month.json` (все числа, действия по ролям, окупаемость).

**Прогон меняет данные:** сид чистит транзакции, поэтому после месяца в базе лежит месяц
(250 закрытых строк). Вернуть витрину: `task proto:seed:showcase`, вернуть состояние для
e2e: `task proto:seed PROCESS=--all`.

## 9. Оговорки

- Значения **синтетические**: объёмы, цены и множители заданы генератором с фиксированным
  `seed`. Смысл — в методе и в сходимости двух расчётов, а не в конкретных рублях.
- Смоделированы **3 процесса из 11** (`happy`, `stock`, `car_repair_in`). Остальные —
  возвраты, отмена закупки, самовывоз, виртуальная закупка — в месяц не входят.
- Нет страховых взносов, аренды, налогов, амортизации, брака и потерь; см. §5.
- Себестоимость запчастей взята из справочника и не пересчитывается по партиям: учёт
  партий в модели не участвует.
- «Вклад роли» — механическая развесовка по узлам карты, а не оценка полезности роли (§4).
