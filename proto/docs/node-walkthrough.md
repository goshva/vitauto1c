# Продвижение строки по узлам через интерфейс

## Коротко

1. Открыть **Строки** — `/lines`.
2. Отметить строку **флажком в первой колонке**. Панель действий появится сама.
3. В панели нажать кнопку перехода. **На каждой кнопке подсказка — номер узла**:
   навести и увидеть «Узел M3».
4. Строка переходит в следующее состояние. Состояние видно в колонке **Статус** плашкой,
   узел — в подсказке кнопки, которой переходили.

Шаги проверены сквозным тестом (`e2e/node-walkthrough.spec.ts`): отметка, появление
кнопки, подсказка с узлом, клик, смена состояния.

## Почему кнопки, а не выпадающий список состояний

**Показаны только те переходы, которые допускает текущее состояние.** Из «Нового» есть
«Зарезервировать» и «Отменить», но нет «Собрано» и «Закрыть». Выпадающий список со всеми
состояниями позволял бы проставить то, чего процесс не допускает, — и строка ушла бы в
состояние, из которого нет пути.

Это проверено тестом: из нового состояния кнопок «Собрано» и «Закрыть» в панели НЕТ.

## Если отмечено несколько строк

Переход показывается, только если его допускают **все** отмеченные строки. Переход,
возможный лишь для части, выносится отдельной строкой: «Недоступно для части строк:
Зарезервировать (1)». Иначе часть строк молча не сдвинулась бы, а выглядело бы это как
успех.

## Таблица переходов: что за кнопка и какой узел

| Кнопка | Состояние | Узел | Из каких состояний |
|---|---|---|---|
| Зарезервировать | `reserve` | **M3** | Новый, В работе |
| На комплектацию | `assembly` | **M9 · G3** | Резерв, На склад, Приёмка, Собрано, Возврат |
| Собрано | `ready_to_ship` | **K3** | Комплектация |
| Самовывоз | `shipped` | **N4** | Оплачен, В пути |
| Принять по УПД | `acceptance` | **K1** | Отгружен |
| Возврат | `return` | **N3 · M16 · K6** | Отгружен, Заказан, Оплачен, В пути, На склад, Закрыт |
| Закрыть | `closed` | **M15 · K7 · G9** | Отгружен, Собрано, Возврат, Комплектация |
| Отменить | `cancelled` | **N2a · M15** | Новый, В работе, Заказан, Оплачен, В пути, Приёмка, … |
| Клиент отказался | `refused` | **N2b** | Собрано, Отгружен |

У некоторых переходов **несколько узлов**: одно и то же действие бывает на разных ветках
процесса. Подсказка перечисляет их через точку — «M9 · G3».

Состояния **Заказан**, **Оплачен** и **В пути** этими кнопками не ставятся: они приходят
из снабжения, а не из реестра строк.

## Полный обход модели: сид ручной проверки

```
bun run db:seed --nodes      # 142 строки: по строке на каждый узел каждого процесса
bun run scripts/verify-nodes.ts   # проверка покрытия
```

Затем в реестре: **каждая строка подписана своим узлом**. Комментарий говорит, где строка
сейчас: «процесс 0 (Основной), шаг 5, узел P1». По нему и видно, что именно проверяешь.

**ВАЖНО: прогон тестов сид затирает.** Тесты чистят строки и движение, и это правильно —
сид ручной проверки не рабочие данные. Порядок такой: засеять, проверить, а тесты гонять
после. Если после тестов сид пропал — засеять снова.

## Проверка покрытия: что она показывает

```
ПОКРЫТИЕ УЗЛОВ
  процессов: 12, узлов: 36, строк по карте: 142, в базе: 142

ПО ПРОЦЕССАМ:
   0  Основной: закупка → отгрузка            18      18  полностью
   1  Со склада (резерв)                      12      12  полностью
   ...
  10  Поступление машины в ремонт             18      18  полностью
  11  Ремонт со склада (без закупки)          11      11  полностью

ПО УЗЛАМ: в карте 36, в базе 36
  не представлены: нет
  неверное число строк: нет
  подпись не совпала с узлом: нет
  несуществующие состояния: нет

ВСЕ УЗЛЫ ВСЕХ ПРОЦЕССОВ ПРЕДСТАВЛЕНЫ.
```

Сверка идёт **с картой процессов**, а не с сидом: сид из карты и сгенерирован, и сверка
его с самим собой ничего не докажет.

Проверяются четыре вещи, и все четыре нужны:

- **строки по процессам**: у каждого процесса каждое его состояние узла представлено;
- **узлы**: все 36 встречаются, и каждый — столько раз, сколько шагов его содержат
  (узел N1 стоит в семи процессах, и строк с ним должно быть семь);
- **подпись**: комментарий называет СВОЙ узел — иначе проверяющий сверяет не то;
- **состояния**: ни одного несуществующего. Это не формальность: у одного шага в карте
  состояния нет, и первая версия генератора подставляла в базу СТРОКУ `'null'` — состояние,
  которого нет ни в модели, ни в переходах.
