# Инструменты: почему ломались команды и что с этим делать

Разбор четырёх повторявшихся ошибок. Все проверены на этой машине, а не предположены.

---

## Короткий вывод

**Проблема не в оболочке, а в передаче КОДА через командную строку.** WSL не нужен,
переход на Git Bash сам по себе не помогает — проверено ниже. Помогает одно:
**писать код в файлы, а командной строке оставить только запуск.**

---

## Что доступно на машине

| Средство | Есть? |
|---|---|
| `bash` (Git Bash) | **да**, `C:\Program Files\Git\bin\bash.exe` |
| `git` | да, `C:\Program Files\Git\cmd\git.exe` |
| `wsl` | **нет**, не установлен |
| `bun` | да |

## Ошибка 1. TypeScript-синтаксис в файле `.mjs`

**Что было:** «Unexpected token `!`», «Unexpected identifier `as`», «Unexpected token `:`».

**Причина:** я писал вспомогательные скрипты как `.mjs` (обычный JS), но по привычке
ставил в них TypeScript-обозначения: `rows[0]!.name`, `as { entries: … }`,
`(indent: string)`.

**К оболочке отношения не имеет.** Bash, PowerShell, что угодно — файл разберёт
JavaScript-движок, и он прав.

**Решение:** вспомогательные скрипты — **`.ts`, запуск через `bun`**. `bun` выполняет
TypeScript напрямую, и причина выбирать `.mjs` отсутствует.

---

## Ошибка 2. Обратные кавычки в SQL-комментарии внутри шаблонной строки

**Что было:** «Expected `)` but found `SET`», «SyntaxError: missing ) after argument list».

**Причина:** SQL лежал в шаблонной строке TypeScript, а в комментарии к нему я писал
`` `CREATE OR REPLACE VIEW` `` — обратные кавычки **закрывали саму строку**.

**К оболочке отношения не имеет** — это содержимое файла.

**Решение:** SQL держать в **`.sql`-файлах**, а не в шаблонных строках. Проект уже
так делает для миграций; два самых болезненных случая (пересборка `line_view`) были
именно там, где я от этого отступил и собирал SQL строками.

Если SQL всё же в коде — **обратных кавычек в комментариях не ставить вовсе.**

## Ошибка 3. Кириллица в SQL ломает psql

**Что было:** `ERROR: invalid byte sequence for encoding "UTF8": 0xd4 0xe8`.

**Причина — НЕ PowerShell.** Проверено: из Git Bash та же ошибка. Байты `0xd4 0xe8` —
это «Фи» в **CP866**. Командная строка Windows перекодирует аргументы в свою
кодовую страницу, и `psql` получает CP866 там, где ждёт UTF-8. `client_encoding`
в базе при этом `UTF8` — дело не в сервере.

**Решение — проверено:** передавать SQL **файлом**.

```bash
psql "$DB" -f query.sql        # кириллица, ёлочки, ёж — всё проходит
```

Ещё лучше для проверок данных: **не звать psql вовсе**, а писать `.ts` с `pool.query`
и запускать через `bun`. Тогда кодировка командной строки не участвует нигде.

**Правило: кириллицы в аргументах командной строки быть не должно.**

## Ошибка 4. `!`, кавычки и `$` в inline-командах

**Что было:** `rows[0]!.purpose` → PowerShell искал команду с таким именем;
`echo "rows[0]!.name"` → `!` и хвост исчезли.

**Причина:** команда проходит через разбор PowerShell **до** того, как её увидит
любая другая оболочка.

**Проверено:** вызов `bash -c 'echo "rows[0]!.name"'` **из PowerShell** даёт тот же
испорченный результат. То есть **смена оболочки не помогает**: PowerShell испортил
строку раньше.

**Решение — проверено:** команда **файлом**.

```
bash script.sh
```

Тест файлом прошёл целиком: `!`, вложенные кавычки, `$` и `$(())`, обратные кавычки,
кириллица, апостроф, `%` — всё сохранилось.

---

## Итог: что делать

| Правило | Что закрывает |
|---|---|
| Скрипты писать `.ts`, запускать `bun` | ошибку 1 |
| SQL держать в `.sql`-файлах | ошибку 2 |
| Кириллицу не передавать в аргументах; для данных — `pool.query` из `.ts` | ошибку 3 |
| Сложную команду писать файлом, а не строкой | ошибку 4 |

**Git Bash оставляем как удобный запускатель файлов** — он корректно печатает
кириллицу в выводе. Но он **не является решением**: два из четырёх случаев
воспроизводятся в нём ровно так же.

**WSL не нужен.** Он не установлен, требует прав и перезагрузки, и не устраняет ни
одну из четырёх причин: три из них — про содержимое файлов, а четвёртая — про
командную строку как способ передачи, а не про её оболочку.
