# Чек-лист P0: четыре правки, без которых прототип нельзя показывать

**Основание:** `docs/analysis-architecture-resilience.md` §4.2 · **Дата:** 18.11.2026

Здесь только P0 — то, что даёт потерю данных, двойной учёт или доступ без входа.
P1/P2 (транзакции переходов, атомарный `If-Match`, таймауты, блокировка заданий, гейты) —
в разборе, §7.

## Порядок и почему он такой

| Шаг | Правка | Трудоёмкость | Зависимости |
|---|---|---|---|
| 1 | **P0-1.** Тестовые хуки смонтированы всегда | ~15 минут | нет |
| 2 | **P0-3.** Двойное проведение приёмки/отгрузки | ~2 часа | нет |
| 3 | **P0-4.** Идемпотентность не защищает от гонки | ~2 часа | нет |
| 4 | **P0-2.** Аноним = администратор | ~день | делать последним: после него придётся править тесты и e2e |

P0-1 идёт первым, потому что это единственная правка, которая закрывает **удалённое
стирание базы** одним условием `if`. P0-2 дороже всех: закрытие доступа ломает и тесты, и
e2e (см. цену в P0-2).

## P0-1. Тестовые хуки смонтированы всегда

**Симптом.** `POST /__test__/seed` с `{"process":"happy","reset":true}` стирает все
транзакционные таблицы и засевает процесс заново. Доступен он **в любом запуске**:
флаг `PROTO_TEST_HOOKS` не читается кодом нигде.

**Доказательство.**
- `src/routes.ts:90` — `app.route('/', testHooks);` без условия.
- `src/test-hooks.ts:28-47` — обработчик; `:43` вызывает `resetTo` (truncate, `db/seed.ts:65-78`).
- Флаг есть только в `playwright.config.ts:54`; комментарии `src/test-hooks.ts:4-12` и
  `src/routes.ts:84-89` утверждают обратное — «только при флаге».
- Проверено вживую на работающем экземпляре: `GET /__test__/seed` → 200 без куки и без заголовков.

**Правка.**

```ts
// src/routes.ts, вместо app.route('/', testHooks);
if (Bun.env.PROTO_TEST_HOOKS === '1') app.route('/', testHooks);
```

Дополнительно (по желанию, но дешевле сделать сразу): в самом хуке отказывать, если не
передан ни `process`, ни явный `reset` — чтобы «случайный» POST ничего не стирал.

**Проверка.**
1. `bun run dev` **без** флага → `GET /__test__/seed` → **404**, `POST` → 404.
2. `PROTO_TEST_HOOKS=1 bun run dev` → 200, сиды работают.
3. `bun run e2e` — зелёный (playwright поднимает свой сервер с флагом, `playwright.config.ts:46-55`).

**Важно, иначе e2e упадёт после правки.** `playwright.config.ts:49` — `reuseExistingServer: true`.
Если на 18190 уже висит сервер, запущенный **без** флага, Playwright переиспользует его, и
`e2e/processes.spec.ts:171` получит 404. Перед прогоном остановите посторонний сервер либо
поставьте `reuseExistingServer: false`.

**Готово, когда:** без флага хуков нет ни по GET, ни по POST; с флагом e2e зелёный;
в `src/routes.ts` условие читается глазом, а не комментарием.

## P0-2. Аноним = администратор

**Симптом.** Запрос без куки и без заголовков получает роль `admin`. Все GET-экраны и
данные отдаются без входа; `guard` стоит только в 32 местах, а `POST /lines/transition`,
`POST /lines/step`, `PATCH /lines/{id}` — вообще без проверки прав.

**Доказательство.**
- `src/auth.ts:27-32` — `role: c.req.header('x-role') ?? 'admin'`.
- Проверено вживую: `/lines` (JSON), `/jobs`, `/audit` → 200 без куки.
- `docs/access-gaps.md:19-23` — замер: 68 GET-адресов, **49 отдают данные без входа**;
  123 вызова в тестах без сессии (замер на момент написания документа).

**Правка — три шага (план уже описан в `docs/access-gaps.md:80-108`).**

1. **Роль только из сессии.** Убрать `?? 'admin'`. Если нужен демонстрационный режим API —
   оставить заголовок `X-Role`, но под отдельным явным флагом (`PROTO_ALLOW_X_ROLE=1`),
   а не по умолчанию.
2. **Одна прослойка на всё приложение** (в `src/server.ts`, до маршрутов): нет сессии →
   HTML ведёт на `/login`, JSON отвечает **401** тем же типом ошибки, что и всё API
   (`Problem` с кодом `unauthorized`, `src/problem.ts:11-33`).
   Исключения: `/health`, `/login`, `/logout`, `/static/*`, `/__test__/seed` (и только под флагом из P0-1).
   Прослойка, а не проверка в каждом обработчике: обработчиков десятки, и новый маршрут
   должен быть закрыт **по умолчанию**.
3. **Тесты.** Общий помощник уже есть — `tests/helpers/request.ts`, его импортируют 47 файлов.
   Осталось 15 «сырых» `app.request(` — заменить на `request(`, кроме тех, что **проверяют**
   закрытость (они обязаны остаться без сессии).

**Цена, которую надо назвать заранее.** В e2e вход упоминается только в `e2e/login.spec.ts`;
**10 из 11 спеков** ходят в UI без входа, а `e2e/processes.spec.ts` работает через API-фикстуру
без куки. После закрытия им нужен общий шаг входа (`storageState` или хелпер логина) —
иначе они уедут на `/login`.

**Проверка.**
1. Без куки: `GET /lines` c `Accept: application/json` → **401**; `GET /lines` в браузере →
   переход на `/login`; `GET /health` → 200.
2. С кукой администратора: поведение как раньше.
3. Тесты, проверяющие закрытость, остались без сессии — и проходят.
4. `bun run e2e` — зелёный.

**Готово, когда:** анонимный клиент не получает ни данных, ни роли; `/health` и `/login`
открыты; новый маршрут закрыт без дополнительного кода.

## P0-3. Двойное проведение приёмки и отгрузки

**Симптом.** Два параллельных `POST /receipts/{id}/post` оба проходят проверку «ещё не
проведено» и оба вставляют движения склада — **остаток удваивается**. Комментарий в коде
обещает обратное.

**Доказательство.**
- `src/receipts-flow.ts:59` — `if (head.posted)` **до** `begin` (`:66`);
  `:100-103` — `update receipt set posted = true … where id = $1` **без `and not posted`**.
- Тот же шаблон: `src/shipments-flow.ts:61` (`checkShipmentTransition` до `begin` на `:66`,
  UPDATE на `:68` — только `where id = $1`), `src/returns-flow.ts:67` (то же, `:74`),
  `src/work-orders-flow.ts:84`; удаление — `returns-flow.ts:134`, `shipments-flow.ts:128`.

**Правка.** Условие состояния должно быть **частью того же UPDATE**, а не отдельным SELECT
до транзакции:

```sql
update receipt
   set posted = true, version = version + 1, updated_at = now()
 where id = $1 and not posted
returning id
```

`rowCount === 0` → откат и `409` с понятным текстом («Приёмка уже проведена»). То же для
отгрузки, возврата и наряда. Проверка `head.posted` до `begin` остаётся только ради
внятного сообщения — решение принимает UPDATE.

**Тесты (новые).**
1. Два параллельных `POST .../post` (или последовательных после «проигранной» гонки) →
   ровно **одно** движение склада, второй ответ — 409.
2. Повторный `POST .../post` по уже проведённому документу → 409, остаток не меняется.

**Готово, когда:** ни один путь проведения не может вставить движения дважды; на каждый
документ есть тест на повтор.

## P0-4. Идемпотентность не защищает от гонки

**Симптом.** `Idempotency-Key` работает как «проверить → выполнить → записать»: два
одновременных запроса с одним ключом оба промахиваются по проверке и оба выполняются.
Второй заказ/приёмка — реальность. Плюс: запись тела идёт **после** коммита операции, и
если процесс упадёт между ними, ключ потерян и ретрай повторит операцию.

**Доказательство.**
- `src/idempotency.ts:29-39` — SELECT, затем `await next()`, затем INSERT (`:49-52`).
- `db/schema/idempotency.ts:23` — `index('idempotency_key_uniq')`, **не** `uniqueIndex`;
  в базе это подтверждено: `CREATE INDEX idempotency_key_uniq … (key, method, path)`.
- `src/idempotency.ts:53-56` — пустой `catch {}`: сбой БД при вставке глотается молча.
- `status` и `body` объявлены `notNull()` (`db/schema/idempotency.ts:17-18`) — то есть
  «строка-резерв без ответа» сейчас невозможна по схеме.
- TTL нет: старый ключ вечно отдаёт устаревшее тело.

**Правка.**

1. Миграция (drizzle-схема + `bun run db:generate`):
   - `uniqueIndex` вместо `index` по `(key, method, path)`;
   - сделать возможным резерв: `status`/`body` — nullable (или добавить `state text not null default 'running'`).
2. Порядок в middleware: **сначала вставка-резерв** `insert … on conflict do nothing returning id`:
   - строка вставлена → выполняем, затем `update … set status, body`;
   - строка уже есть и тело заполнено → реплей (`Idempotent-Replay: true`), как сейчас;
   - строка есть, но тело пусто → **409** «повтор ещё выполняется» (или 425) — вместо второго выполнения.
3. Пустой `catch {}` заменить на логирование (`src/idempotency.ts:53-56`).
4. TTL: удалять ключи старше N суток (например, 7) — иначе ответ недельной давности
   отдаётся как свежий.
5. Отдельно решить и записать: HTML-ответы HTMX-мутаций (`src/lines-ui-actions.ts`) телом не
   сохраняются (`res.clone().json()`), значит эти маршруты **не защищены**. Либо сохранять
   текст, либо явно задокументировать исключение.

**Тесты (новые).**
1. Параллельный реплей: два одновременных запроса с одним ключом → операция выполнена **один раз**.
2. Повтор после «сбоя» между выполнением и записью ключа → не создаёт второй объект.
3. Тот же ключ с **другим телом** → 409 (сейчас ключ не привязан к телу запроса).

**Готово, когда:** уникальность обеспечивает БД, а не порядок запросов; параллельный реплей
доказан тестом.
