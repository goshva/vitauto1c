# API процессов и прав (REST, OpenAPI, Swagger)

Сервис ведёт заказы по сценариям из [process.html](../process.html) и проверяет каждое действие правами ролей из матрицы [index.html](../index.html). Через него же меняются настройки: матрица прав, узлы и сценарии процессов, пользователи API.

Node.js 20+, без внешних зависимостей.

```powershell
cd api
$env:VITAUTO_ADMIN_TOKEN = 'придумайте-токен'   # иначе токен admin сгенерируется и напечатается при первом запуске
npm start                                         # http://127.0.0.1:8787/docs — Swagger UI
npm test                                          # 33 теста
```

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `PORT` | `8787` | порт |
| `HOST` | `127.0.0.1` | адрес; `0.0.0.0` — доступ из сети |
| `VITAUTO_API_DATA` | `api/data` | каталог хранилища `store.json` (в git не попадает) |
| `VITAUTO_ADMIN_TOKEN` | — | токен администратора при первом запуске |

Swagger UI (`/docs`) подгружает скрипты с unpkg.com, поэтому браузеру нужен интернет. Спецификация — `/openapi.json`.

## Откуда берутся данные

При первом запуске сервис читает прототипы:

- **`index.html`** — роли, статусы, колонки;
- **`default-matrix.js`** — права;
- **`column-codes.js`** — коды колонок (`Е4`, `Р2`);
- **`process.html`** — узлы и сценарии.

Дальше настройки живут в хранилище и меняются через API. `POST /settings/reset` возвращает их к прототипам.

## Доступ

`Authorization: Bearer <токен>`. Токен выдаёт администратор (`POST /settings/users`) и показывает один раз. У каждого пользователя API одна роль матрицы: `manager`, `storekeeper`, `chief_mechanic`, `admin`, `supplier`, `client`.

## Правила

| Действие | Кто может |
|---|---|
| Начать заказ по сценарию (`POST /orders`) | роль узла первого шага сценария или `admin` |
| Перейти на следующий шаг (`POST /orders/{id}/advance`) | роль узла следующего шага или `admin` |
| Изменить значения строки (`PATCH /orders/{id}/lines/{lineId}`) | по матрице для роли и текущего статуса: `role` — роли из `editableRoles`, `creator` — автор строки, `admin` — администратор, `none` — никто |
| Перевести на любой шаг (`goto`), переход без обязательных (`force`) | `admin` |
| Менять матрицу, процессы, пользователей; читать журнал | `admin` |

- **Обязательные колонки.** Уйти со статуса нельзя (422), пока не заполнены колонки, обязательные в нём (`required`) для ролей, которые по сценарию работают в этом статусе. Переходы между шагами внутри одного статуса не проверяются: обязательную колонку часто заполняет следующий шаг.
- **Запрещённая колонка.** Если хоть одна колонка в запросе запрещена, не меняется ничего. В ответе 403 в `details.denied` перечислены колонки и причина.
- **Уровень статуса.** `statusLevel` в настройках прав: `order` — права по статусу заказа, `line` — по статусу строки.
- **Статус шага.** Шаг со статусом `null` статус не меняет.
- **Журнал.** Все изменения пишутся в `/audit`.

## Пример

```powershell
$h = @{ Authorization = 'Bearer придумайте-токен' }
$u = 'http://127.0.0.1:8787/api/v1'
$m = Invoke-RestMethod "$u/settings/users" -Method Post -Headers $h -ContentType 'application/json' -Body '{"name":"ivan","role":"manager"}'
$c = Invoke-RestMethod "$u/settings/users" -Method Post -Headers $h -ContentType 'application/json' -Body '{"name":"stroytrans","role":"client"}'
$o = Invoke-RestMethod "$u/orders" -Method Post -Headers @{ Authorization = "Bearer $($c.token)" } -ContentType 'application/json' `
     -Body '{"scenarioId":"happy","lines":[{"values":{"comment":"заявка по фото"}}]}'
Invoke-RestMethod "$u/orders/$($o.id)/actions" -Headers @{ Authorization = "Bearer $($m.token)" }
Invoke-RestMethod "$u/orders/$($o.id)/advance" -Method Post -Headers @{ Authorization = "Bearer $($m.token)" }
```

## Ограничения

- **Сервис не связан с базой 1С.** Заказы живут в его хранилище, АРМ их не видит. Связь с 1С — отдельная задача: через COM, как `seed-1c.ps1`, или через HTTP-сервис расширения после публикации базы на веб-сервере.
- **Типы значений не проверяются:** числа, даты и выбор из списка принимаются как есть. Правила полей матрицы (`fieldRules`: формулы, отборы, автозаполнение) сервис не применяет.
- **Читать заказы могут все роли.** Отбор «клиент видит только свои заказы» не сделан.
- **Ветвления процесса** (`next` у узлов) сохраняются, но заказ идёт только по шагам выбранного сценария. Свернуть на другую ветку может `admin` через `goto`.
- **Сервис однопроцессный, хранилище — один JSON-файл.** Для нескольких экземпляров нужна база данных.
