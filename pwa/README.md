# АРМ закупок и продаж — PWA через OData

Vue 3 + Pinia + Vue Router + vite-plugin-pwa. Данные — **стандартный интерфейс OData 1С**
(расширение `АРМ_OData`, см. [`../odata/README.md`](../odata/README.md)); HTTP-сервис `Арм_API` (АРМ v2.9) больше не нужен.

Экраны и хранилища по-прежнему вызывают операции контракта REST API АРМ (`/lines`, `/matrix`, `/sales/…`,
`openapi/arm-pwa*.openapi.yaml` в ветке `api`), но выполняются они в браузере запросами OData —
[`src/odata/backend.js`](src/odata/backend.js). Логика команд перенесена из `Арм_API`: матрица прав, переходы
процессов, канбан снабжения (закупка ведёт связанную продажу), отметки «только автор», вычёркивание связки строк,
отгрузка, «Подготовлено», В9 «Дата отправки на сборку» при «Комплектуется».

| Файл | Что |
|---|---|
| `src/api.js` | те же `api/get/post`, вызовы уходят в OData-бэкенд; журнал — реальные запросы OData |
| `src/odata/client.js` | запросы OData: Basic-авторизация пользователем ИБ (UTF-8), кодирование кириллицы, `odata.error` → Problem |
| `src/odata/mapping.js` | запись `InformationRegister_Арм_ДанныеЗакупокИПродаж` ↔ строка `Line`, статусы, типы полей, ключ записи |
| `src/odata/backend.js` | 29 операций контракта поверх OData |
| `src/odata/matrix.json` | матрица прав (57 колонок × 15 статусов × 7 ролей) — `python tools/gen_pwa_matrix.py` |

## Запуск

```
npm run api        # Apache с публикацией 1С (D:\1c\apache, :8090) + проверка OData (../odata/start-apache.ps1)
npm run dev        # http://127.0.0.1:5173 — прокси /odata -> ODATA_TARGET (по умолчанию тестовая /odata215)
npm run build && npm run preview   # сборка с service worker: http://127.0.0.1:4173
npm test           # 16 интеграционных тестов против живого OData (экраны + пишущие операции, данные возвращаются)
```

Копия рабочей базы (дамп `autoservice_main`, PostgreSQL 18, сервер 1С `localhostutoservice_main`, публикация `/odata-main`):
`npm run dev:main` (`.env.main`); **рабочая база** `localhost\autoservice` — `npm run dev:prod` (`.env.prod`, `/odata-prod`,
вход «Автосервис» без пароля, роль АРМ «Менеджер» — пользователи из дампа; проверка только чтением — `MAIN_READONLY=1`). Копия: вход — пользователь ИБ «Автосервис» без пароля (роль АРМ «Менеджер»). Проверка:
`npx vitest run -c vitest.e2e.config.js e2e/main-smoke.e2e.js` — вход, матрица, строки, справочники, новый заказ → строки
«Громкоговоритель» → правка, отметка → удаление заказа.

Другая база: `ODATA_TARGET=http://<сервер>/<публикация>/odata/standard.odata npm run dev` (для тестов — `ODATA_URL`).
Публикация: расширение `АРМ_OData` подключено и включено (`../odata/enable-odata.ps1`), в `default.vrd` —
`<standardOdata enable="true" …/>`. В Apache правило токенов API переносит только `Authorization: Bearer`
(иначе Basic до 1С не доходит).

## Интерфейс (mobile-first)

- **Телефон** — нижняя панель разделов (списки роли, «Загрузка», «Ещё»); строки — карточки, сгруппированные по заказам;
  нажатие на карточку — детали строки: документы, действия, все поля матрицы роли с правкой по нажатию
  (текст / число / дата — поле ввода, флажок — переключатель, справочник — выбор из списка).
- **ПК (от 900 px)** — боковая панель; строки — таблица с правкой двойным кликом, детали открываются справа.
- Отмеченные строки — панель снизу с итогами и кнопкой «Действия» (переходы процессов, «В работе», статусы снабжения);
  кнопка «⚡» в шапке открывает те же действия всегда. Поиск — по загруженным строкам, быстрые фильтры — чипы.
- Тема — системная / светлая / тёмная (меню «Ещё» / «Настройки»), учтены safe-area и крупные зоны нажатия.

**Настройка отображаемых полей** (кнопка «Поля») — отдельно для каждой роли и списка, хранится в браузере:

| Вкладка | Что настраивается |
|---|---|
| Карточка | поля под наименованием карточки и их порядок (до 12), набор этапа процесса (process.html), предпросмотр |
| Таблица | колонки: основные / редактируемые ролью / все / этап процесса / свой набор, «скрывать пустые» |
| Детали | сначала поля, которые можно изменить; сворачивать пустые поля только для чтения |
| Вид | список: авто (карточки на телефоне, таблица на ПК) / карточки / таблица; плотность |

## Разделы «Товары», «Услуги», «Машины»

\`/catalog/goods\` (номенклатура «Запас»), \`/catalog/services\` («Услуга»), \`/catalog/cars\` (справочник \`асАвтомобили\`):
поиск, таблица на ПК / карточки на телефоне, карточка с правкой, «+» — новый элемент, удаление — пометка на удаление
(восстанавливается; помеченные — кнопка-корзина в шапке). Цена — вид цен «Розничная цена» (регистр \`ЦеныНоменклатуры\`),
госномер — периодический регистр \`асАвтомобили\`; их, как и создание номенклатуры (\`Заполнить()\` УНФ + умолчания формы),
пишут команды АРМ_OData (\`СоздатьНоменклатуру\`, \`ЦенаНоменклатуры\`, \`ДанныеАвтомобиля\`). Менять: товары — admin, manager,
storekeeper; услуги и машины — admin, manager, chief_mechanic; остальные роли — просмотр.

Загрузка из Excel: \`python ../odata/import-catalogs.py --base <…/standard.odata> --user <пользователь 1С> [--dry-run]\` —
«товар для 1 с.xlsx», «Услуга.xlsx» (как «ТО» в базе: одна услуга на вид работ, цены по шасси — документ
«Установка цен авторабот» на модели шасси, команда `ЦеныАвторабот`; базовая цена — минимальная), «машины для 1 с.xlsx» (группа — вид техники,
модель — \`асМодели\`, госномер). Повторный запуск обновляет, а не дублирует.

Вход — только форма PWA: прокси убирает \`WWW-Authenticate\` из ответов 401 1С, системного окна логина браузера нет.

## Вход и роли

Вход — пользователь ИБ 1С (Basic-авторизация на каждый запрос OData, токен хранится в браузере). Роль АРМ —
регистр `Арм_ПраваПользователей` по элементу «Пользователи» с тем же наименованием. Тестовые пользователи
(пароль `1`): `arm.manager`, `arm.storekeeper`, `arm.supply`, `arm.admin`, `arm.mechanic` —
`..\odata\pwa-test-users.ps1 -IbDir <тестовая база>` (пользователь ИБ + элемент «Пользователи» со связью
`ИдентификаторПользователяИБ` — без неё БСП не даёт записывать документы).

## Команды АРМ (расширение АРМ_OData v1.1)

«В работе» (M4/M13/K5), канбан снабжения с приходной накладной (M7…K3), проведение заказа, новый заказ / импорт
листа (`Заполнить()` 1С) выполняет 1С: бэкенд пишет команду в регистр `InformationRegister_АрмOData_КомандыPWA`,
обработчик записи вызывает код АРМ в сеансе пользователя PWA (см. [`../odata/README.md`](../odata/README.md)).
`POST /sales/jobs` отвечает сразу итогом задания (`done` / `need_split` / `failed`), `GET /jobs/{id}` его возвращает.
Не реализовано: `POST /sales/supplier-orders` — 501 (в АРМ заглушка, заказ поставщику создаёт «В работе»).

Файловая 1С иногда отвечает 500 из «испорченного» сеанса пула («Тип не определен …», «Нельзя сравнивать поля …») —
клиент повторяет чтение, команду — один раз (её транзакция откатилась).

## Сквозные сценарии process.html

```
npm run e2e                        # 11 сценариев, отчёт e2e/processes-report.md (узлы схемы, роли, шаги)
E2E_ONLY=happy,stock npm run e2e   # выборочно; E2E_NOM — номенклатура (по умолчанию «Антифриз»)
```
Порт `tools/arm-api-1c/e2e-processes.js` (REST, ветка `process-api`) на этот бэкенд: роли arm.*, права полей — матрица
`index.html`. Пишет данные (новые заказы) — только тестовая база.

Отличия от `Арм_API`: простые операции (отметки, переходы, PATCH) — несколько запросов OData без общей транзакции;
права матрицы проверяет PWA — сам OData пишет любые поля пользователю с правами на регистр.
