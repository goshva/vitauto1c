## 0. Итоговая оценка покрытия

| Критерий гексагональной архитектуры | Состояние | Оценка |
|---|---|---|
| Доменное ядро без зависимостей от инфраструктуры | Пакет `domain` чистый, но не подключён | ~50 % |
| Ядро в центре (зависимости внутрь) | Инвертировано: центр — `arm`, `domain` — лист | ~15 % |
| Порты (интерфейсы) для репозиториев и сервисов | 4 интерфейса, ни одного репозитория | ~5 % |
| Адаптеры привода (HTTP/WS) отделены | Да, пакет `api` отделён | ~80 % |
| Адаптеры вывода (БД, 1С, WS) отделены | Частично: `onec`, `integration`, `ws` — да; БД — нет | ~40 % |
| Прикладной слой без SQL | Нет: `application` держит `*pgxpool.Pool` | ~20 % |

| Критерий DDD | Состояние | Оценка |
|---|---|---|
| Стратегическое проектирование (контексты, карта) | Задокументировано: 11 контекстов, карта связей | ~85 % |
| Тактическое проектирование (документ) | Агрегаты, VO, события, политики описаны | ~80 % |
| Агрегаты в коде | 1 из 13, и тот не подключён | ~10 % |
| Инварианты в агрегате | Реализованы, но в другом месте (`arm` + БД) | ~25 % |
| Оптимистическая блокировка (`If-Match`) | Объявлена в модели, контракте и коде — не исполняется | ~5 % |
| Доменные события и их диспетчеризация | Объявлены 10, поднимаются 2, обработчиков нет | ~10 % |
| Объекты-значения | Нет: `Money`/`Quantity`/`Pricing` — это `float64` | ~10 % |
| Единый язык (Ubiquitous Language) | Есть глоссарий-генератор | ~70 % |
| Ограниченные контексты в коде | Разбиения нет: слои, а не контексты | ~10 % |
| Трассируемость модель ↔ код ↔ тесты | Генераторы + тесты модели | ~75 % |

**Краткий вывод.** DDD реализован **как документация и как «остров» чистого ядра**, но не как
рабочий путь исполнения. Бизнес-правила фактически живут в трёх местах одновременно:
в пакете `arm` (SQL + правила), в триггерах PostgreSQL и в PWA. Пакет `domain` — параллельная
модель, которую продакшн не использует.

## 1. Доменное ядро (пакет `backend/internal/domain`)

### 1.1 Ядро действительно изолировано

5 файлов, 562 строки, зависимости — только `fmt`, `errors`, `time`, `strings`, `embed`,
`encoding/json`, `github.com/google/uuid`. Ни `pgx`, ни `net/http`, ни обращений к БД или файлам.

- [domain.go](../backend/internal/domain/domain.go) — 73 строки
- [line.go](../backend/internal/domain/line.go) — 181 строка
- [status.go](../backend/internal/domain/status.go) — 133 строки
- [matrix.go](../backend/internal/domain/matrix.go) — 94 строки
- [events.go](../backend/internal/domain/events.go) — 81 строка

Граф зависимостей подтверждает: `domain` не импортирует ни один внутренний пакет.

### 1.2 Перечисления и перевод значений 1С ↔ API

- `Status` — 17 констант значений 1С (status.go:8-30).
- `Operation` — `Продажа` / `Закупка` (status.go:35-38).
- `Status.APICode()` — обратный перевод значения 1С в код REST (status.go:46-82),
  включая схлопывание `Подготовлено`/`Собран` → `ready_to_ship`.
- `StatusFromAPICode()` — прямой перевод (status.go:85-121).
- `RoleByEnum` / `EnumByRole` — 7 ролей интерфейса 1С ↔ роли API (status.go:124-134).
- `IsClosedSale()` — правило «закрытые статусы продаж» (status.go:41-43).

### 1.3 Агрегат `Line` и его инварианты

Корень агрегата описан в line.go:35-79. Признаки настоящего агрегата соблюдены:

- События инкапсулированы: приватное поле `events []Event` (line.go:78), доступ только
  через `Events()` (line.go:82) и `raise()` (line.go:84).
- **`Authorize()`** — единая защита из 5 проверок (line.go:101-131): удалённость, версия
  (оптимистическая блокировка), `ЗаблокированоФоном`, закрытая строка (кроме админа),
  право на поле по матрице роли.
- **`TransitionTo()`** — смена статуса только через автомат, поднимает `LineStatusChanged`
  (line.go:135-149).
- Команды: `Mark()` (line.go:152-161), `Strike()` (line.go:164-169),
  `SetSelfPickup()` (line.go:172-175), `RejectAssembly()` (line.go:178-192).
- Бизнес-формула `SaleSum()` — норма-часы × цена, иначе количество × цена (line.go:90-96).
- `MarkedByMe()` — правило права `c` (только автор пометки) (line.go:87).

Важная оговорка: перечисленное **написано корректно, но не исполняется** — ни один метод
агрегата не вызывается из продакшн-кода (см. раздел 9 и [todo.md](todo.md), P0-1).
В частности, проверка версии (line.go:105-107) существует только здесь: во всём остальном
Go-коде нет ни одного сравнения `where version = $` и ни одной обработки заголовка `If-Match`
(подробнее — [todo.md](todo.md), P0-2a).

### 1.4 Автомат статусов как декларативная таблица

`Transitions` — 10 записей с полями «код перехода, целевой статус, откуда, кому»
(domain.go:33-44). Функции `TransitionsFor()` (domain.go:47-55) и `AllowTransition()`
(domain.go:58-70) возвращают целевой статус либо ошибку. Таблица — данные, а не `switch`.

### 1.5 Таксономия доменных ошибок

10 сентинельных ошибок (line.go:11-23) + структурная `StateError` (line.go:195-200).
Перевод в HTTP выполнен в прикладном слое: `AsProblem()` (application/service.go:80-101)
даёт 404/409/403 по типу ошибки. Это правильный признак: домен не знает про HTTP.

### 1.6 Матрица прав как доменная политика

`MatrixColumn`, `MatrixFor()`, `MatrixETag()`, `DenyReason()`, `ColumnFor()`
(matrix.go:20-105). Матрица встроена в бинарь через `//go:embed matrix.json` (matrix.go:15-16),
то есть домен не читает файлы во время работы. `DenyReason()` реализует символы `+` / `c` / `.`
(matrix.go:67-95).

### 1.7 Доменные события объявлены

`Event` — маркерный интерфейс с приватным методом `eventName()` (events.go:8).
10 типов: `LineStatusChanged`, `AssemblyRequested`, `AssemblyRejected`, `GoodsPlaced`,
`SelfPickupRecorded`, `LineAssembled`, `Shipped`, `GoodsReceived`, `StockMoved`,
`MatrixChanged` (events.go:10-103).

## 3. Адаптеры

### 3.1 Адаптер привода — HTTP/WS (`backend/internal/api`)

Отделён от ядра: `App` собирает сервисы как зависимости
(handlers.go:16-21: `ARM`, `Auth`, `Apps`, `WS`). Регистрация маршрутов вынесена в
`Register`/`RegisterV2`/`RegisterV3` (handlers.go:90, handlers_v2.go:17, handlers_v3.go:13).

Контракт «снаружи внутрь»:

- `api/openapi.yaml` — 111,7 КБ, `api/asyncapi.yaml` — 5,5 КБ.
- `internal/api/types.gen.go` — 1 901 строка моделей, сгенерированных oapi-codegen.
- `Pinger` — интерфейс-порт для проверки БД, внедряется в `NewMux` (server.go:22-27).
  Это единственный настоящий порт в бэкенде.

### 3.2 Адаптеры вывода — отделены

| Адаптер | Пакет | Что изолирует |
|---|---|---|
| 1С (ACL) | `internal/onec` (4 файла) | GUID, перечисления, составные типы, `_IDRRef`; не тянет БД |
| Очередь в 1С | `internal/integration/outbox.go` | Идемпотентная отправка через OData-регистр команд |
| WebSocket | `internal/platform/ws/` (hub, listener, handler) | Сигнальная инвалидация через `LISTEN/NOTIFY` |
| Миграция 1С→PG | `internal/migrate/` (5 файлов) | Перенос данных, сверка |

Идемпотентность outbox заявлена явно: ссылка на `entity_id` (outbox.go:1-9, 47-52).

### 3.3 Веб-клиент — частично порт

- `pwa/src/api.js` — единая фасадная функция `api(method, path, {query, body})` (api.js:66),
  выбор транспорта по базовому URL (api.js:12, 68).
- `pwa/src/odata/client.js` — настоящий адаптер OData (кодирование URL/запроса,
  `odata.error` → `ApiError`, повтор при 500).
- `pwa/src/odata/errors.js` — `ApiError` приведён к форме REST `Problem`, поэтому
  представления не знают о транспорте.
- `pwa/src/http/schema.d.ts` — 4 135 строк контракта, сгенерированных openapi-typescript.
- Хранилища Pinia вызывают только `api` (например, `pwa/src/stores/lines.js`).

## 5. Доменные политики и инварианты — реализованы, но в БД

Это важный раздел: часть политик из `02-tactical.md` **работает**, однако исполняется
триггерами PostgreSQL, а не обработчиками доменных событий.

Инвентарь: 12 различных функций (13 определений — `arm.line_status_notice` переопределена
в 0010_ws_notify.sql:6), 9 триггеров, 2 представления. Процедур, генерируемых столбцов
и exclusion-ограничений нет.

| Правило | Где реализовано | Соответствие модели |
|---|---|---|
| Уведомления M8/M9/M10/M11/M17/K9 | `arm.line_status_notice()` (0005_notify.sql:50-76; переопределена 0010:6-29) | Политики из 02-tactical.md:82-93 |
| Дедупликация уведомлений (одно на узел+роль+заказ за день) | `arm.notice_add()` (0005_notify.sql:13-46, правило на 31-40) | Агрегат `Notice` |
| Инвариант «ЧастичноЗаказано» | `arm.partial_ordered_sync()` (0015_partially_ordered.sql:22-95) | Статус из матрицы № 2 |
| Доставка уведомлений в WS | `arm.notice_notify()` (0010:35-46) | `Notice` → WS |
| Инвалидация WS по строкам | `sys.line_change()` (0011_ws_changes.sql:52-66) | сигналы A0 |
| Инвалидация WS по документам | `sys.notify_change()` (0011_ws_changes.sql:8-22) | возвраты, заказ-наряды, неопознанные |
| Сигнал по решению доступа | `sys.access_request_change()` (0011:34-47) | A3 |
| Уведомление о запросе доступа | `auth.access_request_notice()` (0009:30-47) | `RightsRequested` |

Триггер `arm.partial_ordered_sync()` — образцовый пример: правило описано в комментарии
(0015:8-13), защищено от рекурсии (0015:32-34), срабатывает на всех путях записи (0015:18-19).
При этом он **меняет статус в обход автомата** (0015:87) — то есть FSM из `domain` не является
единственным способом смены статуса.

Обратите внимание: **запись уведомлений существует только в БД**. Поиск
`insert into arm.notice` по всему Go-коду не даёт совпадений; `arm/notices.go` только читает
и отмечает прочитанным. То есть политики уведомлений исполняются целиком вне приложения.

### 5.1 Что в БД реализовано корректно

- **Очередь outbox**: `integration.outbox` (0004_app.sql:60-73) с полями
  entity/entity_id/payload/status/attempts/error/sent_at и индексом `(status, created_at)`.
  Запись — в той же транзакции, что и изменение (arm/docs.go:31); разбор — `FOR UPDATE SKIP LOCKED`
  со статусами new/failed → sent/dead (integration/outbox.go:96-138).
- **Аудит удаления** — обобщённая схема без дублирования в каждой таблице (0017:7-25).
- **Ограничения-перечисления** через CHECK: операция возврата (0006:19), источник неопознанной
  позиции (0007:20), статус заказ-наряда (0008:26), статус запроса доступа (0009:19),
  признаки номенклатуры (0013:39-43).
- **Функции перевода 1С** в схеме `onec` — `uuid(bytea)`, `uuid(text)`, `type_no`, `ts`
  (0001:74-95), совпадающие по алгоритму с `backend/internal/onec`.

## 8. Что из гексагональной архитектуры сделано правильно

1. **Доменное ядро без инфраструктуры.** `domain` не знает ни о БД, ни об HTTP — 0 запрещённых импортов.
2. **Единая точка защиты инвариантов** в агрегате: `Line.Authorize()` вместо разрозненных проверок.
3. **Автомат статусов как данные**, а не как ветвление кода.
4. **Таксономия ошибок домена** отделена от HTTP-кодов; маппинг — в прикладном слое.
5. **Адаптеры вывода вынесены** для 1С, очереди и WebSocket; ACL для 1С изолирует понятия платформы.
6. **Адаптер привода вынесен**: HTTP-слой собирает зависимости через структуру `App`.
7. **Порт `Pinger`** внедряется в маршрутизатор — позволяет поднять сервис без БД.
8. **Идемпотентная очередь (outbox)** для интеграции с бухгалтерией.
9. **Модель предметной области — источник истины** для генерации документов и тестов,
   с проверкой в CI.
10. **Единый язык** зафиксирован глоссарием, связывающим процесс, 1С, API и БД.
11. **Модель чтения отделена** представлением `arm.line_api`.
12. **Схемы БД разложены по контекстам**, что создаёт предпосылку для разбиения кода.
13. **Клиент нормализует ошибки** (`ApiError` → форма REST `Problem`), представления
    не зависят от транспорта.
