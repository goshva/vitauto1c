# АРМ_OData — полный стандартный интерфейс OData

Расширение `АРМ_OData` (`АРМ_OData_v1.1.cfe` в корне репозитория) включает в стандартный интерфейс OData **все**
объекты основной конфигурации и подключённых расширений, включая объекты АРМ (`Арм_*`).

| Файл | Назначение |
|---|---|
| `АрмOData_Интерфейс.bsl` | общий модуль расширения: `ВключитьПолныйСоставOData()`, `ТекущийСоставOData()`, `КоличествоКандидатовOData()` |
| `АрмOData_Команды.bsl`, `АрмOData_КомандыPWA.RecordSet.bsl` | v1.1: команды АРМ через OData — регистр `АрмOData_КомандыPWA` (см. ниже) |
| `build-odata-ext.ps1` | сборка расширения из модуля (XML → тестовая база → `.cfe`) |
| `enable-odata.ps1` / `enable-odata.js` | включение полного состава в базе через COM (снимает безопасный режим `АРМ_OData`) |
| `odata-check.ps1` | проверка публикации OData и сверка с операциями PWA; отчёт — `odata-check-report.md` |

## Как включить

```text
1. Подключить АРМ_OData_v1.1.cfe к базе (конфигуратор → Расширения конфигурации или build-odata-ext.ps1 -IbDir <база>)
2. .\odata\enable-odata.ps1 -IbDir <каталог базы>        # или -ConnectionString 'Srvr="localhost";Ref="autoservice";Usr="Администратор";Pwd=""'
3. Публикация: в default.vrd
     <standardOdata enable="true" reuseSessions="autouse" sessionMaxAge="20" poolSize="10" poolTimeout="5"/>
   Адрес: http://<сервер>/<публикация>/odata/standard.odata/   (Basic-авторизация пользователем ИБ)
4. .\odata\odata-check.ps1 -BaseUrl http://127.0.0.1:8090/<публикация> -User Админ [-Write]
```

Apache (`D:\1c\apache\httpd-1c.conf`): правило для токенов API АРМ должно переносить только `Authorization: Bearer …`
(`SetEnvIf Authorization "^(Bearer .+)$" ARM_AUTH=$1`). Прежнее `"(.+)"` убирало и Basic — OData получал 401.

## Команды АРМ через OData (v1.1)

Стандартный OData только читает и пишет данные. Команды с логикой АРМ выполняет запись в регистр сведений
`АрмOData_КомандыPWA` (измерение `Ид`; ресурсы `Команда`, `Параметры`, `Результат` — JSON, `Успешно`, `Пользователь`,
`ДатаВыполнения`): `ПередЗаписью` набора выполняет команду в сеансе OData — под пользователем PWA, с его отметками.

```text
POST InformationRegister_АрмOData_КомандыPWA  {"Ид":"cmd-…","Команда":"ВРаботе","Параметры":"{\"allowSplit\":true}"}
  200 -> запись, Результат = {"state":"done","message":…}
  500 -> odata.error «…АРМODATA{"status":409,"code":"nothing_marked","message":…}» (отказ; запись не сохраняется)
```

| Команда | Параметры | Что делает (код АРМ) | Узлы process.html |
|---|---|---|---|
| `ВРаботе` | `allowSplit` | `Арм_ДанныеЗакупокИПродажФон.СформироватьЗаказыФоновоеЗадание`: заказы поставщику, проведение заказа, расходные накладные, сплит | M4, M13, K5 |
| `СтатусСнабжения` | `status`, `partialReceipt`, `receiptDate` | `ИзменитьСтатусыВРегистреСнабжения` (жёсткая цепочка, продажа за закупкой, на «Собран» — приходная накладная) | M7, P2, K1, K2, M9, K3 |
| `ПровестиЗаказ` | `id` | строки «Подготовлено» → «Запасы», пустые реквизиты — `Заполнить()`, проведение, строки → «Завершено» | M15 |
| `СоздатьЗаказ` | `customerId`, `contractId`, `clientOrderNumber`, `date`, `rows[]` | `Заполнить()` (организация, склад, валюта …), состояние — первое по виду заказа, строки АРМ — обработчиком АРМ | N1, M1 |

Почему не фоновое задание: в файловой базе сеанс пула OData, запустивший задание, теряет типы расширений
(«Тип не определен '…'» на любые запросы), а ожидание задания внутри транзакции записи — взаимоблокировка.
Отказ команды записать нельзя: процедуры АРМ откатывают свои (вложенные) транзакции, поэтому он приходит ошибкой OData.

## Развёртывание серверной базы из дампа: `deploy-autoservice-pg.ps1`

```text
.\odata\deploy-autoservice-pg.ps1 -Dump D:\dump-autoservice_main-202610121429.sql            # рабочая localhostutoservice
.\odata\deploy-autoservice-pg.ps1 -Dump … -Infobase autoservice_main -IbUser Автосервис -AdminRole Менеджер `
    -ODataUrl http://127.0.0.1:8090/odata-main/odata/standard.odata -SkipBackup                # копия
```
pg_dump текущей БД → запрет сеансов и регламентных заданий → DROP/CREATE + pg_restore → перезапуск службы сервера 1С →
`АРМЗакупокИПродаж_v2.15.cfe` и `АРМ_OData_v1.1.cfe` (/LoadCfg -Extension, /UpdateDBCfg), оба включены
(`ext-activate.js`: активно, без безопасного режима, роль АРМ) → полный состав OData → seed `import-catalogs.py --fill-arm`:
товары, услуги (+ цены авторабот по шасси), машины из Excel и строки АРМ по заказам покупателей за последний год
(команда `ЗаполнитьАРМ`: ключи строк «Запасы» без перепроведения + штатная `ОбновитьДанныеПоОбъекту`; закупки для позиций
без остатка добавляет сам АРМ). Проверено на копии (14.10.2026): 19 строк продаж и 3 закупки за год, 1229 товаров,
7 услуг, 154 машины. Сервер 1С пишет кэш на диск C — нужно свободное место (кэш рабочей базы ~4 ГБ).

## Тесты запросов и ответов: `test_odata.py`

```text
python odata/test_odata.py                         # ODATA_URL (по умолчанию http://127.0.0.1:8090/odata215), ODATA_USER, ODATA_PASSWORD
python odata/test_odata.py -k Filter               # выборочно
```
47 тестов: сервис и `$metadata`, авторизация (401), ошибки (404/400 с `odata.error`), `$top/$skip/$count/$inlinecount/
$select/$orderby/$expand`, `$filter` (строки, перечисления, числа, даты, guid, булево, and/or/not, навигация,
`substringof/startswith/endswith/like` и ещё 20 функций OData v3), доступ по ключу (справочник, документ,
составной ключ регистра АРМ), табличные части, журналы, константы, `SliceLast`, `Balance/Turnovers`, `Post()/Unpost()`,
запись (справочник: POST/PATCH/DELETE; регистр АРМ: PATCH, POST, DELETE), скорость. Пишущие тесты убирают за собой.
Отчёт — `test-odata-report.md`: что не работает, и все запросы с кодом, временем и началом ответа.

Результат 13.10.2026 (`/odata215`, Apache :8090): **48 тестов, прошло 37, не работает 11**:

| Не работает | Что | Обход |
|---|---|---|
| функции `$filter`: `indexof`, `length`, `tolower`, `toupper`, `trim`, `replace`, `floor`, `ceiling` | 1С: HTTP 400 «Функция не поддерживается» | поиск — `substringof`/`startswith`/`endswith`/`like` (регистр букв 1С и так не учитывает); округление — на клиенте |
| `$expand` у одиночной сущности (`Document_X(guid'…')?$expand=…`) | HTTP 501 «Опция $expand не поддерживается при запросе одиночных сущностей» | коллекция с `$filter=Ref_Key eq guid'…'` + `$expand` (так делает PWA) |
| `PATCH` с несуществующим полем | HTTP 200, поле молча пропущено — опечатка в имени не видна | клиент сверяет имена полей с `$metadata` |
| проведение заказов из seed | `Post()` доходит до обработки проведения, но заказ SEED-* не проводится: пустая Организация и Номенклатура в строках «Запасы» (seed пишет номенклатуру только в строки АРМ) | доработать seed: организация и номенклатура в документе |

Работает: строки поиска без учёта регистра (как в языке запросов 1С), перечисления в `$filter` по имени
(`СтатусСтроки eq 'Черновик'`), поле составного типа — `Поле` + `Поле_Type` (не `Поле_Key`), перечисления — не наборы,
а типы в `$metadata`; первый запрос после запуска Apache — до 2 мин (1С строит модель), дальше 10–300 мс.

## PWA и OData

PWA (`pwa/`, ветка `pwa-odata`) работает через OData: операции контракта REST API АРМ выполняет
`pwa/src/odata/backend.js` (чтение и простые записи — запросами OData, логика АРМ — командами v1.1).
Сквозная проверка всех 11 сценариев `process.html` по ролям матрицы `index.html` — `cd pwa && npm run e2e`,
отчёт `pwa/e2e/processes-report.md`.
