# План миграции АРМ vitauto: 1С → PostgreSQL + Go + Vue 3 PWA

Ветка: `migration/pg-go-vue`, создана от `techdebt/arm-v2.22` на коммите 83723cb (АРМ v2.23 и АРМ_OData 1.3).
Дата: 2026-10-30.

Цели:
1. Перенести учёт АРМ закупок и продаж на собственный стек: PostgreSQL, бэкенд на Go и уже существующая PWA на Vue 3.
2. Не потерять ни одной записи базы 1С.
3. Добавить универсальный импорт табличных данных.
4. Сделать склады и ячейки полноценной частью интерфейса.

---

Цифры сняты 2026-10-30 с копии `vitauto_dev`, это рабочая база по состоянию на 28.10.

| Ячейки | у ARM-строки только строковое поле `ЯчейкаСклада`; справочника ячеек нет |
| Данные АРМ | регистр `Арм_ДанныеЗакупокИПродаж` (68 полей), `Арм_ПраваПользователей`, `Арм_Уведомления`, `АрмOData_КомандыPWA`, журнал АРМ |
| PWA | Vue 3.5, Pinia 3, vue-router 4, Vite 7, vite-plugin-pwa |

Что важно для архитектуры:

- **Объём данных маленький.** Всего около 256 тыс. живых строк, поэтому полную выгрузку можно повторять хоть каждую ночь. Вся миграция строится на повторяемом и идемпотентном прогоне.
- **У PWA уже есть свой REST-контракт.** Экраны вызывают `/lines`, `/selection`, `/sales/*`, `/print`, `/notifications`, `/catalog/*`, `/directories/*`, `/documents/*`, `/jobs/*`, `/matrix`, `/session`. Эти вызовы переводит в OData модуль `pwa/src/odata/backend.js`. Если Go реализует тот же контракт, PWA переключится на него без переписывания экранов, а сквозные тесты `tools/e2e/arm-processes.e2e.js` (37 сценариев) станут критерием готовности для обоих бэкендов.
- **«Автосервис» шире АРМ.** В нём есть заказ-наряды, касса и ККТ, регламентированный учёт и отчётность. Объём, который заменяет новый стек, нужно зафиксировать отдельно (раздел 9). План по умолчанию исходит из гибридного варианта.

## 2. Принципы «без потери данных»

1. **Ничего не удаляется до приёмки.** Сохраняются:
   - база `vitauto` в 1С;
   - её дамп `pg_dump`;
   - выгрузка `.dt`;
   - образ конфигурации `.cf` с расширениями `.cfe`.

   После переключения 1С переводится в режим «только чтение» и хранится не меньше срока исковой давности. Решение по сроку за владельцем.
2. **Два слоя переноса.**
   - **Типизированный слой.** Объекты, с которыми работает новое приложение, раскладываются в нормальные таблицы с внешними ключами.
   - **Архивный слой `legacy`.** Сюда попадает каждый непустой объект метаданных 1С, в том числе тот, что приложению не нужен: одна строка на объект или запись, всё содержимое в `jsonb`, вместе с табличными частями и представлениями ссылок. Так ничего не теряется, даже если что-то забыли включить в типизированную схему.
3. **Идентификаторы сохраняются.**
   - GUID ссылки 1С (`Ref_Key`) становится первичным ключом `uuid` в новой базе.
   - Коды и номера документов переносятся как есть.
   - Для перечислений хранится имя значения (`Комплектуется`), а не порядковый номер.
4. **Повторяемость.** Мигратор каждый раз строит базу заново из источника, а сверка обязана давать ноль расхождений. Ручные правки данных в целевой базе до переключения запрещены; исправления вносятся в правила маппинга.
5. **Сверка обязательна** перед каждым показом и перед переключением (раздел 6). Отчёт сверки — артефакт приёмки.
6. **Прод не трогаем.** Как и в работе над АРМ, вся разработка идёт на копиях (`vitauto_dev` и новые). Читать из `vitauto` можно только на этапе финальной выгрузки, после заморозки.

## 3. Целевая архитектура

```
 ┌──────────────┐  HTTPS   ┌──────────────────────────────┐  pgx   ┌──────────────────────┐
 │ PWA Vue 3    │ ───────▶ │ Go: vitauto-api              │ ─────▶ │ PostgreSQL vitauto_app│
 │ (тот же код, │  REST    │  • REST-контракт PWA         │        │  схемы: ref, doc,     │
 │ backend=http)│ ◀─SSE─── │  • матрица прав, статусы     │        │  stock, arm, imp,     │
 └──────────────┘          │  • фон. задания, уведомления │        │  auth, legacy         │
                           │  • печать (html/template)    │        └──────────────────────┘
                           │  • импорт (xlsx/csv)         │                   ▲
                           └──────────────────────────────┘                   │
                           ┌──────────────────────────────┐   OData/COM       │
                           │ Go: vitauto-migrator (CLI)   │ ◀── 1С vitauto ───┘
                           │  extract → load → reconcile  │
                           └──────────────────────────────┘
```

| Слой | Выбор | Почему |
|---|---|---|
| СУБД | PostgreSQL 18, отдельная база `vitauto_app` на отдельном экземпляре (порт 5434) | не пересекается с кластером 1С; та же версия, уже знакомая эксплуатации |
| Миграции схемы | `goose`, SQL-файлы в `db/migrations` | простой, версионируемый, без ORM |
| Доступ к данным | `pgx/v5` и `sqlc` (типизированный код из SQL) | без ORM, запросы видны и проверяются при сборке |
| HTTP | стандартный `net/http` (роутинг Go 1.22+) и `chi`-middleware при необходимости | минимум зависимостей |
| Аутентификация | логин и пароль (bcrypt), сессионный токен в `auth.session`, роли из `Арм_РолиИнтерфейса` | пароли 1С не выгружаются: пользователи задают их при первом входе |
| Права | перенос матрицы `Арм_МатрицаПрав` и `pwa/src/odata/matrix.json` в таблицу и проверка на сервере в одной функции | сейчас проверки разнесены: PWA, `ОтказЗаписиOData`, модуль формы; в Go — одна точка |
| Фоновые задания | таблица `arm.job` и воркер в процессе (`FOR UPDATE SKIP LOCKED`) | заменяет `Арм_ДанныеЗакупокИПродажФон`; контракт `/sales/jobs` → `/jobs/{id}` сохраняется |
| Уведомления | таблица `arm.notice`, выдача через SSE `/events` и опрос `/notifications` | правила M8, M9, M10, M11, K9/M17 из `Арм_УведомленияСервер` |
| Печать | `html/template`, печать браузером; PDF по желанию через headless Chromium | сейчас PWA уже получает HTML из `Арм_ПечатьСервер.ВHTML` |
| Импорт | `excelize` (xlsx), `encoding/csv` | раздел 7 |
| Фронтенд | существующая `pwa/`; новый модуль `src/http/backend.js` и переключатель `VITE_BACKEND=go\|odata` | экраны и хранилища не меняются |
| Поставка | два бинарника Go под Windows Server (службы через `sc`/winsw), Apache или Caddy раздаёт `pwa/dist` и проксирует `/api` | без Docker, как на текущем сервере; Docker-вариант по желанию |

Структура репозитория в ветке:

```
backend/            Go-модуль vitauto
  cmd/api/          HTTP-сервер
  cmd/migrator/     extract | load | reconcile | legacy
  internal/arm/     строки, статусы, матрица, разделение, подбор партий
  internal/stock/   склады, ячейки, движения, остатки
  internal/imp/     импорт
  internal/print/   печатные формы
  internal/onec/    клиент OData 1С для мигратора
db/migrations/      SQL goose
db/queries/         SQL для sqlc
pwa/                как есть + src/http/backend.js
docs/migration/     карта данных, отчёты сверки, регламент переключения
```

## 4. Модель данных (целевая)

### 4.1 Справочники (`ref`)

| Таблица | Источник 1С | Примечание |
|---|---|---|
| `ref.organization` | Организации | |
| `ref.counterparty` | Контрагенты | ИНН, КПП, признаки покупатель/поставщик |
| `ref.contract` | ДоговорыКонтрагентов | FK на контрагента и организацию |
| `ref.nomenclature` | Номенклатура | артикул, ед. изм., вид (товар/услуга), группа (иерархия `parent_id`) |
| `ref.batch` | ПартииНоменклатуры | владелец партии = поставщик |
| `ref.unit` | КлассификаторЕдиницИзмерения | |
| `ref.price_type`, `ref.price` | ВидыЦен, ЦеныНоменклатуры (регистр сведений, периодический) | история цен сохраняется полностью |
| `ref.car`, `ref.car_model` | асАвтомобили, асМодели, регистр сведений асАвтомобили | марка, модель, VIN, госномер |
| `ref.service_kind`, `ref.payment_form` | Арм_ВидыУслуги, Арм_ФормыОплаты | |
| `ref.labor_price` | асЦеныАвторабот | |
| `ref.user` | Пользователи + пользователи ИБ | связь с ролью АРМ |
| **`ref.warehouse`** | СтруктурныеЕдиницы (тип «Склад») | новое в интерфейсе, раздел 8 |
| **`ref.storage_cell`** | уникальные значения `ЯчейкаСклада` | новое: ячейка как справочник |

Все таблицы имеют поля:
- `id uuid` (= Ref_Key 1С);
- `code`;
- `name`;
- `deleted` (= ПометкаУдаления);
- `onec_ref uuid` (для объектов, созданных в 1С);
- `created_at` и `updated_at`.

### 4.2 Документы (`doc`)

Шапка и табличные части выделены в отдельные таблицы:
- `doc.customer_order` и `doc.customer_order_line`;
- `doc.supplier_order` и `…_line`;
- `doc.receipt` (ПриходнаяНакладная) и `…_line`;
- `doc.shipment` (РасходнаяНакладная) и `…_line`.

Прочие виды документов из 19 непустых, например заказ-наряды и кассовые документы, попадают в `legacy`, пока для них не выбрано решение по разделу 9.

Статус проведения переносится как `posted bool`. Движения документов в 1С не пересчитываются: переносятся сами записи регистров, раздел 4.3.

### 4.3 Склад (`stock`)

- **`stock.move`** — движения: дата, документ-регистратор (тип и id), склад, ячейка, номенклатура, партия, заказ покупателя, количество (±) и сумма (±). Источник — движения регистра `Запасы`.
- **`stock.balance`** — представление или материализованный итог по ключу (склад, ячейка, номенклатура, партия, заказ). Проверяется сверкой с `Запасы.Остатки` 1С на дату переключения.
- **`stock.reserve`** — резервы, если они ведутся отдельным регистром; иначе это движения с заполненным заказом.

### 4.4 АРМ (`arm`)

- **`arm.line`** — один к одному с `Арм_ДанныеЗакупокИПродаж`:
  - все 68 полей;
  - `ИдентификаторЗаписи` становится `id`;
  - `ВидОперации` и `СтатусСтроки` хранятся как имена перечислений;
  - `КлючСвязиСтрок` связывает продажу с её закупками;
  - **добавлены** `warehouse_id` и `cell_id`; старое строковое `ЯчейкаСклада` сохраняется в `cell_legacy`.
- `arm.user_rights` ← `Арм_ПраваПользователей`; `arm.matrix` ← матрица прав колонок и статусов.
- `arm.notice` ← `Арм_Уведомления`; `arm.journal` ← журнал АРМ; `arm.job` — фоновые задания.

### 4.5 Архив (`legacy`)

```sql
create table legacy.object (
  kind      text not null,   -- 'Справочник', 'Документ', 'РегистрСведений', ...
  name      text not null,   -- имя объекта метаданных
  key       text not null,   -- Ref_Key или сериализованный ключ записи регистра
  data      jsonb not null,  -- все реквизиты, табличные части, представления ссылок
  loaded_at timestamptz not null default now(),
  primary key (kind, name, key)
);
```

Сюда попадают все 216 + 19 + 166 + 14 непустых объектов и константы, в том числе уже разложенные в типизированные таблицы. Так типизированную загрузку можно перепроверить по архиву. Выдача архива в интерфейсе: экран «Архив 1С» с поиском по объекту и ключу, только чтение.

## 5. Перенос данных (мигратор)

### 5.1 Источники

1. **OData 1С** (`/odata/standard.odata`) — основной источник. Он отдаёт `Ref_Key`, табличные части, перечисления по именам и уже опубликован (`odata/enable-odata.ps1`). Для архивного слоя публикуются все непустые объекты; их список строится автоматически, см. 5.2.
2. **COM** (`V83.COMConnector`, как в `tools/*.js`) нужен для того, чего OData не отдаёт:
   - пользователи ИБ и их роли;
   - структура хранения (`ПолучитьСтруктуруХраненияБазыДанных`) для контроля;
   - остатки регистров на дату (`Запасы.Остатки`) для сверки.

   Скрипт COM пишет JSON, Go его загружает.
3. **Прямое чтение таблиц 1С в PostgreSQL** (`_Reference232` и т.д.) — только как резервный канал и для сверки количества строк. Основным каналом он не годится: имена таблиц обезличены, а байты GUID в `_IDRRef` переставлены относительно `Ref_Key`. Конвертер покрывается тестом.

### 5.2 Шаги `vitauto-migrator`

| Команда | Что делает |
|---|---|
| `inventory` | COM: все объекты метаданных и число записей → `docs/migration/inventory.json`; объектов с данными должно получиться 216/19/166/14 |
| `enable-odata` | публикует в OData все непустые объекты (вызов `odata/enable-odata.js` со списком из inventory) |
| `extract` | OData → `extract/<дата>/<объект>.jsonl`, постранично (`$top`/`$skip`, сортировка по `Ref_Key`), с контрольным числом записей |
| `legacy` | `extract/*` → `legacy.object` (upsert) |
| `load` | `extract/*` → типизированные схемы по правилам `backend/internal/migrate/mapping/*.go`, в одной транзакции; ссылки без пары в справочнике → отчёт `orphans`, а загрузка падает |
| `derive` | склады из СтруктурныхЕдиниц, ячейки из уникальных `ЯчейкаСклада`, связь `arm.line` → склад и ячейка (по умолчанию «Основной склад») |
| `reconcile` | сверка, раздел 6 → `docs/migration/reconcile-<дата>.md`; при любом расхождении код возврата ≠ 0 |
| `delta --since` | повторная выгрузка изменённых объектов (по `DataVersion` и дате изменения) для финального переключения |

Все шаги работают с копией 1С. На этапе 10 их повторяют на замороженной `vitauto`.

### 5.3 Пользователи и пароли

Пароли ИБ 1С хранятся как хеш и выгружаться не будут. Переносятся:
- логин;
- ФИО;
- роль АРМ;
- права из `Арм_ПраваПользователей`.

При первом входе пользователь задаёт пароль по одноразовой ссылке или коду, который выдаёт администратор. Учётные записи `arm.*` для тестов создаются сидом.

## 6. Сверка (критерий «без потери»)

| № | Проверка | Порог |
|---|---|---|
| R1 | число записей по каждому из непустых объектов: 1С (inventory) = `legacy.object` | 0 расхождений |
| R2 | число записей в типизированных таблицах = в источнике (по каждому маппингу) | 0 |
| R3 | хеш содержимого (SHA-256 канонизированного JSON) по каждой записи `legacy` = хеш из повторной выгрузки | 0 |
| R4 | все внешние ключи разрешены, сирот нет | 0 |
| R5 | остатки `Запасы.Остатки` на дату по ключу (склад, номенклатура, партия, заказ): количество и сумма = `stock.balance` | 0 |
| R6 | итоги документов (сумма и количество строк) = сумма табличных частей в новой базе | 0 |
| R7 | `arm.line`: все 68 полей совпадают с 1С; из ссылочных сравнивается id | 0 |
| R8 | выборочная глубокая проверка: 50 случайных документов и 50 справочников, сравнение представлений «как видит пользователь» | 0 |
| R9 | e2e `arm-processes` на Go-бэкенде с данными после миграции | все сценарии зелёные (кроме известных зависимостей от сида, перечисленных в отчёте) |

Отчёт сверки кладётся в `docs/migration/` и прикладывается к акту приёмки.

## 7. Импорт табличных данных

Сейчас импорт есть только у листа покупателя (`POST /sales/imports`, вставка через Tab или «;»). Он заменяется универсальным механизмом.

### 7.1 Возможности

- **Источники:** файл `.xlsx` (выбор листа), `.csv` (разделитель и кодировка UTF-8/1251 определяются автоматически) или вставка из буфера.
- **Сопоставление колонок с полями.** По заголовкам предлагается автоматически (словарь синонимов: «Артикул», «Код товара», «Кат. номер»…), правится вручную и сохраняется как **шаблон импорта** (`imp.template`).
- **Предпросмотр с проверкой.** Каждая ячейка проверяется по типу, обязательности, ссылке («контрагент не найден» → создать или выбрать) и дублям. Ошибки подсвечиваются, строки с ошибками можно исключить.
- **Режимы:**
  - только создавать;
  - создавать и обновлять (upsert по ключу: артикул, код, ИНН, VIN/госномер);
  - только обновлять.
- **Пробный прогон** считает, сколько записей будет создано, обновлено и пропущено, и ничего не пишет.
- **Транзакционность.** Партия импорта (`imp.batch`) пишется целиком или не пишется. Каждая изменённая запись ссылается на партию.
- **Откат партии.** Созданные записи удаляются, обновлённые возвращаются к прежнему значению из `imp.batch_row.before jsonb`. Это возможно, пока на запись нет ссылок из более поздних документов.
- **Права.** Импорт по каждому виду данных разрешается ролью в матрице.
- **Журнал:** кто, когда, файл, результат.

### 7.2 Виды импорта (первая очередь)

| Вид | Ключ | Источник-образец в репо |
|---|---|---|
| Номенклатура (товары) | артикул и производитель | `товар для 1 с.xlsx`, `Шаблон для   деталей.xlsx` |
| Услуги и нормо-часы | код или наименование | `Услуга.xlsx` |
| Автомобили | VIN, госномер | `машины для 1 с.xlsx` |
| Контрагенты и договоры | ИНН+КПП | — |
| Цены (по виду цены и дате) | номенклатура, вид цены, период | — |
| Прайс поставщика (цена закупки, срок) | поставщик, артикул | — |
| **Начальные остатки по складам и ячейкам** | склад, ячейка, номенклатура, партия | — |
| Лист покупателя → заказ и строки АРМ | (как сейчас `/sales/imports`) | экран «Импорт» |

### 7.3 API

```
POST /imports/parse        файл → листы, заголовки, первые 50 строк
POST /imports/preview      {kind, templateId|mapping, rows} → проверка по строкам
POST /imports              {kind, mapping, mode, dryRun} → партия
GET  /imports/{id}         статус и отчёт; POST /imports/{id}/rollback
GET/POST /imports/templates
```

Экран PWA «Импорт» (`ImportView.vue`) получает мастер «файл → сопоставление → проверка → загрузка» и историю партий.

## 8. Склады в интерфейсе

Сейчас склад один и скрыт: заказ получает его из `Заполнить()` 1С, а ячейка — это свободный текст. Что добавляется:

**Справочники**
- «Склады»: наименование, адрес, ответственный, признак «основной», активность.
- «Ячейки»: склад, код (`A-01-03`), зона, вместимость (необязательно), блокировка.
- Массовое создание ячеек по шаблону (ряд, стеллаж, полка) и импорт по 7.2.

**Права по складам**
- `arm.user_warehouse`: кладовщик видит и меняет только свои склады, а администратор — все.
- Связь со снабжением: «Снабжение и Кладовщик» видят общие уведомления в пределах склада.

**Строки АРМ и документы**
- **Фильтр** «Склад» в списке строк (`LinesView`) и в итогах выделения.
- **Склад и ячейка в карточке строки** (`LineSheet`): выбор из справочника вместо текста; правило матрицы — правит кладовщик.
- **Приёмка (K-узлы):** склад и ячейка размещения указываются при «На склад», то есть закрывается блок 5 плана v2.23 (K2, размещение).
- **Подбор партий** (`Арм_ОбщегоНазначенияАРМ`, остатки) учитывает склад строки; есть настройка «искать на других складах», и тогда предлагается перемещение.

**Остатки и складские операции**
- **Остатки:** экран «Остатки» по складу, ячейке, номенклатуре и партии со свободным, зарезервированным и «в пути» количеством. Источник — `stock.balance`.
- **Перемещение** между складами и ячейками: документ `doc.transfer` → `stock.move` (−/+). Статусы и печать «Лист перемещения».
- **Инвентаризация** (вторая очередь): документ, лист пересчёта, акт расхождений.

**Печать**
- Сборочный лист (K3) группируется по складу и сортируется по ячейке.
- Ведомость (M12) показывает склад отгрузки.

**Миграция**
- Все текущие строки и движения получают «Основной склад».
- Ячейки создаются из существующих строк `ЯчейкаСклада`: пустые и мусорные значения попадают в отчёт, а не в справочник.

## 9. Объём замены 1С — решение владельца

«Автосервис» ведёт не только АРМ. Нужно выбрать один из вариантов:

| Вариант | Что в новом стеке | Что остаётся в 1С | Риск и трудоёмкость |
|---|---|---|---|
| **A. Гибрид (рекомендуется для первого этапа)** | АРМ закупок и продаж, справочники, склад, импорт, печать | бухгалтерия, касса и ККТ, регламентированная отчётность; новый стек раз в день выгружает в 1С документы продаж и поступлений | низкий; 1С остаётся учётной системой для отчётности |
| B. Полная замена | всё, включая заказ-наряды, кассу, ККТ (54-ФЗ), отчётность | только архив | высокий: ККТ, ЭДО и отчётность — отдельные проекты |
| C. Только АРМ без склада | строки АРМ | остатки и документы в 1С (интеграция в обе стороны) | средний: двусторонний обмен сложнее, чем A |

**Дальше план исходит из варианта A.** Для него нужен модуль обмена «новый стек → 1С» (этап 9). Его простая форма — HTTP-выгрузка документов в 1С через OData: `Document_РасходнаяНакладная` и `Document_ПриходнаяНакладная`. Нужное уже опубликовано.

## 11. Переключение и откат

1. **Параллельная работа, 2–3 недели.**
   - 1С остаётся основной системой.
   - Каждую ночь мигратор пересобирает `vitauto_app` с копии свежего бэкапа и прогоняет сверку.
   - Ключевые пользователи (менеджер, снабжение, кладовщик) повторяют в новой системе свои действия на тестовом экземпляре.
   - Расхождения превращаются в задачи.
2. **Готовность к переключению:**
   - 5 ночных сверок подряд без расхождений;
   - e2e зелёные;
   - нет открытых блокирующих ошибок;
   - пользователи обучены;
   - инструкция в `docs/migration/cutover.md`.
3. **Окно переключения**, вечер пятницы:
   - (a) объявление и выход пользователей;
   - (b) полный бэкап `vitauto` (`backup-1c-full.ps1`);
   - (c) запрет записи в 1С: роли АРМ без права изменения, PWA переводится в режим «только чтение»;
   - (d) `extract` → `legacy` → `load` → `reconcile` по замороженной базе;
   - (e) проверка: сверка равна нулю и R9 зелёный;
   - (f) PWA переключается на `VITE_BACKEND=go`, публикуется;
   - (g) включается обмен с 1С (вариант A).
4. **Откат** в течение первой недели.
   - Если найдена блокирующая ошибка, PWA возвращается на `odata`, и 1С снова открывается на запись.
   - Данные, введённые в новой системе после переключения, переносятся обратно скриптом `vitauto-migrator export-onec`, который пишет строки АРМ через OData. Это пишется и проверяется на копии **до** переключения.
5. **После приёмки:** 1С остаётся только для чтения (вариант A — учётная система), а дампы архивируются вне сервера.

## 12. Риски

| Риск | Мера |
|---|---|

| Юридически значимые документы и ККТ | вне объёма варианта A |

## 13. Правила ветки

- Ветка `migration/pg-go-vue` ведётся отдельно от доработок АРМ в 1С (`techdebt/arm-v2.22`). Исправления 1С-части (`src-xml`, `.cfe`) делаются в своей ветке, а сюда попадают merge-ем, чтобы мигратор и e2e шли по актуальной логике.
- PWA меняется только аддитивно: новый бэкенд и новые экраны. Режим `odata` работает до этапа 10.
- Каждый этап — отдельный коммит или серия коммитов с префиксом `MIG <этап>:` и обновлением строки статуса ниже.
