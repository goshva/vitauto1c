Что важно для архитектуры:

- **Объём данных маленький.** Всего около 256 тыс. живых строк, поэтому полную выгрузку можно повторять хоть каждую ночь. Вся миграция строится на повторяемом и идемпотентном прогоне.
- **У PWA уже есть свой REST-контракт.** Экраны вызывают `/lines`, `/selection`, `/sales/*`, `/print`, `/notifications`, `/catalog/*`, `/directories/*`, `/documents/*`, `/jobs/*`, `/matrix`, `/session`. Эти вызовы переводит в OData модуль `pwa/src/odata/backend.js`. Если Go реализует тот же контракт, PWA переключится на него без переписывания экранов, а сквозные тесты `tools/e2e/arm-processes.e2e.js` (37 сценариев) станут критерием готовности для обоих бэкендов.
- **«Автосервис» шире АРМ.** В нём есть заказ-наряды, касса и ККТ, регламентированный учёт и отчётность. Отсюда раздел 14 об интеграции с бухгалтерией.
- **GUID в таблицах 1С хранится с переставленными байтами.** Правило перевода проверено на реальной записи: Номенклатура «НФ-00000001» имеет `Ref_Key = dba691ea-8fc9-11f0-8dd6-00155d003609`, а в `_IDRRef` лежит `8dd6 00155d003609 11f0 8fc9 dba691ea`. Формула приведена в разделе 5.2.

## 2. Принципы «без потери данных»

1. **Ничего не удаляется до приёмки.** Сохраняются:
   - база `vitauto` в 1С;
   - её дамп `pg_dump`;
   - выгрузка `.dt`;
   - образ конфигурации `.cf` с расширениями `.cfe`;
   - выгрузка журнала регистрации 1С (он лежит в файлах сервера, а не в базе).

   После переключения 1С переводится в режим «только чтение» и хранится не меньше срока исковой давности. Решение по сроку за владельцем.
2. **Два слоя переноса.**
   - **Типизированный слой.** Объекты, с которыми работает приложение, раскладываются в таблицы с внешними ключами. Каждое поле 1С, не названное в карте, попадает в столбец `extra jsonb` той же строки. Поэтому типизированная таблица тоже ничего не теряет.
   - **Архивный слой `legacy.object`.** Сюда попадает каждая запись каждого непустого объекта метаданных, со всеми табличными частями и представлениями ссылок.
3. **Идентификаторы сохраняются.**
   - UUID ссылки 1С становится первичным ключом.
   - Коды и номера переносятся как есть.
   - Для перечислений хранится имя значения.
4. **Повторяемость.** Мигратор каждый раз строит базу заново из источника, а сверка обязана давать ноль расхождений. Ручные правки целевой базы до переключения запрещены; исправления вносятся в правила (генератор карты и маппинг Go).
5. **Сверка обязательна** перед каждым показом и перед переключением (раздел 9).
6. **Прод не трогаем.** Разработка идёт на копиях (`vitauto_dev`). Читать из `vitauto` можно только на этапе 11, после заморозки.

Правила монорепозитория:
- **Порядок изменения контракта.** Сначала меняется `api/openapi.yaml`, затем `task gen` генерирует Go-интерфейсы и TS-типы PWA (`openapi-typescript` → `pwa/src/http/schema.d.ts`). Сгенерированный код коммитится, и CI проверяет, что `task gen` не даёт изменений.
- **CI на каждый push** выполняет:
  - `gofmt` и `golangci-lint`;
  - `go test ./...` с PostgreSQL 18 в сервис-контейнере;
  - `vitest`;
  - `spectral lint api/*.yaml`;
  - e2e против собранного `vitauto-api` с базой из `db/seed`;
  - сборку артефактов: `vitauto-api.exe`, `vitauto-migrator.exe`, `pwa-dist.zip`.
- **Версия общая** (тег `vX.Y.Z`): в ответе `/api/v1/health`, в PWA и в миграторе. `CHANGELOG.md` ведётся в корне.
- **CODEOWNERS:** `api/` и `db/migrations/` требуют ревью владельца.

## 5. Новая база данных: имена, UUID, соглашения

### 5.1 Схемы и имена

| Схема | Что в ней |
|---|---|
| `ref` | справочники и нормативные данные: номенклатура, контрагенты, договоры, склады, ячейки, цены, автомобили |
| `doc` | документы и их табличные части |
| `stock` | движения и остатки, перемещения, инвентаризация |
| `arm` | строки АРМ, статусы, матрица прав, уведомления, задания, журнал |
| `imp` | шаблоны и партии импорта |
| `auth` | пользователи, сессии, роли, доступ к складам |
| `integration` | outbox, сопоставление объектов, журнал обмена |
| `sys` | журнал изменений для WS, настройки, файлы, протокол миграции |
| `legacy` | полный архив 1С (`legacy.object`) и стенограммы выгрузок |
| `onec` | служебные функции перевода (`onec.uuid(bytea)`) и промежуточные таблицы `onec.stg_*` |

Правила именования:
- **Таблицы:** английский `snake_case`, единственное число, по смыслу (`ref.nomenclature`, `doc.customer_order`). Табличная часть получает имя `<документ>_<часть>` (`doc.customer_order_item`, `doc.shipment_item`).
- **Внешний ключ:** `<сущность>_id` (`counterparty_id`, `warehouse_id`).
- **Ссылка составного типа 1С** (`Регистратор`, `ДокументОснование`, `Заказ`) хранится парой `<имя>_type text` + `<имя>_id uuid`, где `_type` — имя целевой таблицы (`doc.customer_order`). Целостность проверяет триггер и сверка R4.
- **Имена колонок строки АРМ** — это `snake_case` имён REST-контракта PWA (`customerOrder` → `customer_order_id`, `stockCell` → `cell_legacy` / `cell_id`). Так API и база говорят одними словами.
- **Полное соответствие** «таблица 1С → таблица PostgreSQL 1С (`_reference368x1`) → целевая таблица → каждое поле» генерируется в `docs/migration/storage-map.md`. Это и есть инструкция по полям.
- **Происхождение каждого столбца** мигратор записывает в комментарий (`COMMENT ON TABLE/COLUMN`), например: `1С: Справочник.Номенклатура.Артикул (_reference368x1._fld…)`. Источник поля виден прямо в базе (`\d+ ref.nomenclature`).

Общие столбцы каждой типизированной таблицы:

```sql
id           uuid primary key,          -- 5.2
version      bigint not null default 1, -- оптимистическая блокировка и события WS (раздел 11)
created_at   timestamptz not null default now(),
updated_at   timestamptz not null default now(),
deleted      boolean not null default false,  -- ПометкаУдаления
onec_version text,                       -- ВерсияДанных 1С на момент переноса (для delta)
extra        jsonb not null default '{}', -- поля 1С, не названные в карте
import_batch_id uuid null                -- партия импорта (раздел 12), если запись создана импортом
```

### 5.2 UUID

| Случай | Значение `id` |
|---|---|
| Объект 1С со ссылкой (справочник, документ) | **тот же UUID, что `Ref_Key` в OData и `УникальныйИдентификатор()` в 1С** |
| Табличная часть документа | `uuidv5(ns_tp, <id документа> + ':' + НомерСтроки)`: детерминированный, повторный прогон даёт тот же id |
| Запись регистра без ссылки (движения, цены, автомобили) | `uuidv5(ns_reg, <имя регистра> + ':' + <ключ записи>)`; ключ = регистратор + номер строки или период + измерения; исходный ключ хранится в `onec_key text unique` |
| Строка АРМ | UUID из `ИдентификаторЗаписи`, если это корректный GUID; иначе `uuidv5(ns_arm, ИдентификаторЗаписи)`, а исходное значение пишется в `onec_record_id` |
| Новые объекты после переключения | `uuidv7()` (PostgreSQL 18): сортируемый по времени |

Перевод из хранения 1С (резервный канал чтения и сверка R1). Проверен на `vitauto_dev`, проверка G0.3:

```sql
create function onec.uuid(b bytea) returns uuid language sql immutable as $$
  select (substr(h,25,8)||'-'||substr(h,21,4)||'-'||substr(h,17,4)||'-'||substr(h,1,4)||'-'||substr(h,5,12))::uuid
  from encode(b,'hex') h
$$;
-- пустая ссылка 1С (16 нулевых байт) -> NULL
```

Пространства имён `ns_tp`, `ns_reg` и `ns_arm` — фиксированные UUID в `backend/internal/onec/ns.go`. Менять их нельзя.

### 5.3 Типы

| Тип 1С | PostgreSQL | Правило |
|---|---|---|
| Строка(n) | `text` (+ `check (length(..) <= n)` для кодов и номеров) | хвостовые пробелы строк фиксированной длины обрезаются |
| Число(p,s) | `numeric(p,s)` | точность как в 1С |
| Дата | `date` или `timestamptz` (по составу даты в метаданных) | `0001-01-01` → `NULL` |
| Булево | `boolean` | |
| Ссылка | `uuid` + FK | пустая ссылка → `NULL` |
| Перечисление | `text` + FK на `sys.enum_value(enum, name)` | хранится **имя** значения 1С; код API берётся из справочника значений |
| Составной тип | `<имя>_type text` + `<имя>_id uuid` (или `<имя>_value jsonb` для примитивов) | |
| ХранилищеЗначения | `sys.file` (bytea + sha256) и ссылка `file_id` | выгружается через COM: OData его не отдаёт |

Статусы строк АРМ хранятся без потерь. Таблица `arm.line_status` содержит по одной строке на каждое значение `Арм_СтатусыАРМ`: `name` (`Подготовлено`), `code` (`prepared_1c`) и `api_status` (`prepared`). В 1С два значения, «Подготовлено» и «Собран», отображаются в один статус API. В базе хранится исходное значение, а склейка происходит только в API.

## 7. Инструкции по миграции сущностей

### 7.1 Общий алгоритм для каждой сущности

**A1. Инвентаризация.**
- Сущность должна быть в `storage-map.json` (`rule`, `target`, `order`) и в `inventory.json` с числом записей в 1С.
- Если сущности нет в карте, загрузка останавливается.

**A2. Выгрузка.**
- Запрос: `GET /odata/standard.odata/<EntitySet>?$format=json&$orderby=<ключ>&$top=1000&$skip=N`.
- Набор: `Catalog_*`, `Document_*`, `Document_*_<ТЧ>`, `InformationRegister_*`, `AccumulationRegister_*_RecordType`.
- Ответ пишется в `extract/<run>/<EntitySet>.jsonl`.
- Число строк должно совпасть с `rows` из инвентаризации, иначе выгрузка падает.
- Объекты, которых нет в OData, публикуются (`odata/enable-odata.js`).
- `ХранилищеЗначения` выгружается через COM в `extract/<run>/files/`.

**A3. Архив.**
- Каждая запись попадает в `legacy.object` с хешем.
- Табличные части вкладываются в запись владельца.

**A4. Преобразование** по `storage-map.json`:
- переименование полей;
- пустые ссылки и даты → `NULL`;
- перечисления → имена;
- составные → `_type` + `_id`;
- обрезка строк;
- неназванные поля → `extra`;
- `id` по 5.2.

**A5. Загрузка.**
- `COPY` в `onec.stg_<таблица>`.
- `INSERT … ON CONFLICT (id) DO UPDATE` в целевую таблицу в порядке `order`.
- Всё в одной транзакции, внешние ключи `DEFERRABLE INITIALLY DEFERRED`, поэтому циклы (контрагент ↔ договор) допустимы.
- Сироты (ссылка без строки) → отчёт, и транзакция откатывается.

**A6. Пост-проверка сущности:**
- число записей;
- внешние ключи;
- хеши `legacy`;
- специальные проверки из таблицы 7.2.

**A7. Протокол.** В `sys.migration_run` пишутся:
- run id и сущность;
- выгружено, загружено;
- полей в `extra` и ошибок;
- время.

**A8. Комментарии к столбцам.** Мигратор обновляет `COMMENT ON` по `storage-map.json`.

## 10. API и документация (OpenAPI / Swagger)

- **Источник истины — `api/openapi.yaml` (OpenAPI 3.0.3).** Версия 3.0.3, а не 3.1: генератор oapi-codegen (kin-openapi) поддерживает 3.1 не полностью; переход — без изменения контракта, когда поддержка появится. Основа — прежний контракт `openapi/arm-pwa*.openapi.yaml` из ветки `api`. Описываются:
  - все маршруты текущего контракта PWA из `backend.js`: `/session`, `/matrix`, `/lines`, `/lines/{id}`, `/lines/{id}/mark`, `/lines/transition`, `/lines/reject-assembly`, `/selection`, `/sales/jobs|prepared|shipments|imports|customer-orders…`, `/supply/status`, `/print`, `/notifications`, `/notifications/read`, `/jobs/{id}`, `/documents/{kind}/{id}`, `/directories/{name}`, `/catalog/{goods|services|cars}…`;
  - новые: `/warehouses`, `/cells`, `/stock`, `/transfers`, `/imports*`, `/integration/*`, `/admin/*`, `/changes`, `/ws`, `/health`.
- **Префикс** `/api/v1`, версия в `info.version` = версия монорепозитория.
- **Ошибки** — `application/problem+json` (RFC 9457) с полями `code` и `message`, совместимыми с текущим `ApiError` PWA (`unauthorized`, `forbidden_column`, `matrix_denied`, `conflict`, `not_found` …).
- **Безопасность:** `bearerAuth` (сессионный токен); роль и ограничения по столбцам описаны в `x-arm-roles` у операций.
- **Примеры** (`examples`) есть у каждой операции. Те же примеры используются в контрактных тестах.
- **Swagger UI** на `/api/docs`: страница `vitauto-api` загружает `swagger-ui-dist` точной версии с jsDelivr, спецификацию — с самого сервиса (`/api/v1/openapi.yaml`, встроена через `go:embed`). На стенде доступен всем, в проде только роли admin. Статическая документация `docs/api/index.html` (redoc) собирается в CI.
- **События WebSocket** описаны в `api/asyncapi.yaml` (AsyncAPI 3.0) и тоже выводятся на `/api/docs/ws`.
- **Генерация:**
  - `oapi-codegen` (strict server) делает Go-интерфейсы, и неописанный маршрут не компилируется;
  - `openapi-typescript` делает `pwa/src/http/schema.d.ts`.
- **Контроль в CI:**
  - `spectral lint`: 0 ошибок;
  - тест паритета: каждый маршрут таблицы маршрутизации `backend.js` есть в спецификации;

## 11. Обновление данных в реальном времени (WebSocket)

Задача: если пользователь изменил данные со своего устройства, у остальных пользователей открытые страницы обновляются сами. Перезагружать страницу не нужно, а чужие правки не затираются.

### 11.1 Сервер

1. **Журнал изменений.** Каждая типизированная таблица, которую видит интерфейс (`arm.line`, `doc.*`, `ref.*`, `stock.balance`, `arm.notice`, `arm.matrix_*`, `auth.user_role`), имеет триггер `AFTER INSERT/UPDATE/DELETE`:
   - он увеличивает `version`;
   - пишет в `sys.change_log`: `seq bigserial`, `entity`, `id`, `op`, `version`, `fields text[]` (изменённые столбцы), `user_id`, `session_id`, `at`;
   - вызывает `pg_notify('vitauto_changes', seq)`.

   Всё это происходит в той же транзакции, поэтому событие появляется только после фиксации.
2. **Хаб в `vitauto-api`.**
   - Держит `LISTEN vitauto_changes`, читает новые строки журнала и рассылает их подписанным клиентам.
   - Пачки фоновых заданий (разделение, автозакупки) склеиваются за 200 мс в одно событие со списком id.
   - Несколько экземпляров API работают одновременно, потому что каждый слушает PostgreSQL.
3. **Соединение `GET /api/v1/ws`.**
   - Токен передаётся в первом сообщении `{type:"auth", token}`.
   - Проверяется `Origin`.
   - Пинг раз в 25 с.
   - Apache проксирует его через `mod_proxy_wstunnel`.
4. **Подписки клиента.** Клиент присылает `{type:"subscribe", topics:[…]}`:
   - `lines` (с фильтром вида и склада);
   - `line:<id>`;
   - `document:<kind>:<id>`;
   - `catalog:<name>`;
   - `stock:<warehouse>`;
   - `notices`;
   - `matrix`;
   - `session`.

   Сервер отдаёт только события, которые пользователь вправе видеть: по роли, матрице и складам (`auth.user_warehouse`).
5. **Сообщение об изменении:**

   ```json
   {"type":"change","seq":1842,"entity":"line","op":"update","ids":["…"],"version":{"…":17},
    "fields":["status"],"by":{"id":"…","name":"Кладовщик"},"session":"…"}
   ```

6. **Оптимистическая блокировка.**
   - `PATCH /lines/{id}` и другие изменения требуют `If-Match: <version>`.
   - Если версия устарела, ответ `409 conflict` с текущей записью, списком изменённых полей и автором. Так правки, внесённые одновременно, не теряются.
7. **Повтор после разрыва.**
   - Клиент переподключается с `{type:"resume", seq}`, и сервер досылает события из `sys.change_log` (хранятся 24 ч).
   - Если пропуск больше, сервер шлёт `{type:"resync"}`, и клиент полностью перечитывает данные.
   - Если WebSocket недоступен, работает опрос `GET /changes?since=seq` раз в 10 с.

### 11.2 Клиент (PWA)

Новый модуль `pwa/src/http/realtime.js` и хранилище Pinia `realtime`:

| Событие | Поведение страницы |
|---|---|
| изменена видимая строка, пользователь её не редактирует | строка перечитывается (`GET /lines?ids=…`) и заменяется в хранилище `lines`; изменённые поля коротко подсвечиваются |
| изменена строка, открытая в `LineSheet` с несохранёнными правками | баннер «Строку изменил Кладовщик: Статус, Ячейка»; непересекающиеся поля подтягиваются, пересекающиеся показываются как «ваше / новое» с выбором; сохранение со старой версией сервер отклонит (409) |
| строка удалена или ушла из фильтра (сменился статус) | убирается из списка с уведомлением |
| появилась новая строка, подходящая под фильтр | список перечитывается (с задержкой 300 мс) |
| изменена карточка документа или справочника | `DocumentView` и `CatalogView` перечитывают запись |
| `notices` | колокольчик обновляется сразу (вместо опроса раз в 60 с) |
| `matrix` или роль пользователя | матрица перечитывается, интерфейс перестраивается **принудительно** |
| пользователь отключён администратором | сессия закрывается |
| `app_version` (выкладка новой PWA) | баннер «Доступна новая версия», обновление service worker |
| собственное событие (тот же `session`) | только обновляется `version`, без перерисовки |

### 11.3 Проверка

e2e-сценарии `r01`–`r05` с двумя сессиями в одном тесте:

| Сценарий | Что проверяет |
|---|---|
| r01 | A меняет статус строки, у B она обновляется ≤ 2 с без перезагрузки |
| r02 | A и B правят цену одной строки, второй получает 409 и баннер, данные первого не потеряны |
| r03 | разрыв соединения у B, правки A, переподключение B: события досланы по `seq` |
| r04 | администратор меняет роль B: матрица у B перестроена, запрещённые колонки скрыты |
| r05 | B без доступа к складу 2 не получает событий по нему |

Нагрузка: 50 клиентов и 100 изменений в секунду, задержка p95 < 1 с.

## 12. Импорт табличных данных

### 12.1 Возможности

- **Источники:** файл `.xlsx` (выбор листа), `.csv` (разделитель и кодировка UTF-8/1251 определяются автоматически) или вставка из буфера.
- **Сопоставление колонок с полями.** По заголовкам предлагается автоматически (словарь синонимов: «Артикул», «Код товара», «Кат. номер»…), правится вручную и сохраняется как **шаблон импорта** (`imp.template`).
- **Предпросмотр с проверкой.** Каждая ячейка проверяется по типу, обязательности, ссылке («контрагент не найден» → создать или выбрать) и дублям. Ошибки подсвечиваются, строки с ошибками можно исключить.
- **Режимы:**
  - только создавать;
  - создавать и обновлять (upsert по ключу: артикул, код, ИНН, VIN/госномер);
  - только обновлять.
- **Пробный прогон** считает, сколько записей будет создано, обновлено и пропущено, и ничего не пишет.
- **Транзакционность.** Партия импорта (`imp.batch`) пишется целиком или не пишется. Каждая изменённая запись ссылается на партию (`import_batch_id`). Изменения уходят в `sys.change_log`, и открытые страницы обновляются по разделу 11.
- **Откат партии.** Созданные записи удаляются, обновлённые возвращаются к прежнему значению из `imp.batch_row.before jsonb`. Это возможно, пока на запись нет ссылок из более поздних документов.
- **Права.** Импорт по каждому виду данных разрешается ролью в матрице.
- **Журнал:** кто, когда, файл, результат.

### 12.2 Виды импорта (первая очередь)

| Вид | Ключ | Источник-образец в репо |

| Услуги и нормо-часы | код или наименование | `Услуга.xlsx` |
| Автомобили | VIN, госномер | `машины для 1 с.xlsx` |

## 13. Склады в интерфейсе

Сейчас склад один и скрыт, а ячейка — свободный текст. Справочник `Ячейки` в 1С пуст. Что добавляется:

**Справочники**
- «Склады» (`ref.warehouse`): наименование, адрес, ответственный, признак «основной», активность.
- «Ячейки» (`ref.storage_cell`): склад, код (`A-01-03`), зона, вместимость (необязательно), блокировка.
- Массовое создание ячеек по шаблону (ряд, стеллаж, полка) и импорт по 12.2.

**Права по складам**
- `auth.user_warehouse`: кладовщик видит и меняет только свои склады, а администратор — все.
- То же ограничение действует на события WebSocket.

**Строки АРМ и документы**
- **Фильтр** «Склад» в `LinesView` и в итогах выделения.
- **Склад и ячейка в карточке строки** (`LineSheet`): выбор из справочника вместо текста; правило матрицы — правит кладовщик.
- **Приёмка:** склад и ячейка размещения указываются при «На склад» (блок 5 плана v2.23, узел K2).
- **Подбор партий** учитывает склад строки; есть настройка «искать на других складах», и тогда предлагается перемещение.

**Остатки и складские операции**
- **Остатки:** экран по складу, ячейке, номенклатуре и партии со свободным, зарезервированным и «в пути» количеством.
- **Перемещение** между складами и ячейками: `doc.transfer` → `stock.move` (−/+), печать «Лист перемещения». Перемещение уходит в бухгалтерию (раздел 14), если там ведётся складской учёт.
- **Инвентаризация** (вторая очередь).

**Печать**
- Сборочный лист (K3) группируется по складу и сортируется по ячейке.
- Ведомость (M12) показывает склад отгрузки.

**Миграция**
- Все строки и движения получают «Основной склад».
- Ячейки создаются из уникальных `ЯчейкаСклада`: пустые и мусорные значения попадают в отчёт `derive`, а не в справочник.

### 14.1 Варианты

| Вариант | Что в новом стеке | Бухгалтерия | Риск и трудоёмкость |
|---|---|---|---|

| A′. Гибрид с 1С:Бухгалтерией 3.0 | то же | отдельная база БП 3.0 | средний: сопоставление по ИНН и артикулу, формат EnterpriseData |
| B. Полная замена | всё, включая кассу и ККТ (54-ФЗ), отчётность | только архив | высокий: ККТ, ЭДО и отчётность — отдельные проекты |

Ниже описан вариант A. Коннектор устроен так, что A′ добавляется вторым адаптером.

### 14.2 Механизм

- **Transactional outbox.** Проведение отгрузки, приёмки, возврата или перемещения пишет в той же транзакции строку `integration.outbox`:
  - `id`, `target`, `entity`, `entity_id`, `version`;
  - `payload jsonb`;
  - `status` (new / sent / posted / failed / dead), `attempts`, `next_try_at`, `error`.

  Событие не теряется, даже если 1С недоступна.
- **Воркер обмена** раз в минуту:
  - отправляет документ в 1С через OData (`Document_РасходнаяНакладная`, `Document_ПриходнаяНакладная` …) с **`Ref_Key` = наш UUID**. Повторная отправка идемпотентна: если документ уже есть, выполняется PATCH;
  - затем вызывает проведение (`/Post`);
  - при ошибке делает повтор с экспоненциальной паузой; после 10 попыток статус `dead` и уведомление администратору.
- **Что уходит в 1С:**
  - контрагенты, договоры, номенклатура, партии — созданные или изменённые в новой системе, по UUID;
  - отгрузка → Расходная накладная;
  - приёмка → Приходная накладная;
  - возвраты;
  - перемещение между складами;
  - счёт на оплату (по желанию).
- **Что приходит из 1С:**
  - оплаты (банк и касса) → `arm.line.paid` и статусы оплаты заказа;
  - номера и даты УПД и счетов-фактур;
  - **дата запрета изменения** → `integration.period_lock`. Документы закрытого периода в новой системе не редактируются, исправление идёт корректировкой (M19).
- **Сопоставление** `integration.object_map(local_id, target, remote_id, remote_type)`. Для варианта A это тождество; для A′ ключи такие: ИНН+КПП, артикул, номер договора.
- **Журнал обмена в интерфейсе** (роль admin и бухгалтер):
  - очередь, ошибки, просмотр отправленного payload и ответа 1С;
  - «Повторить», «Отправить заново», «Пометить как обработанное вручную».
- **Сверка с бухгалтерией.** Каждую ночь, отчёт `integration/reconcile`:
  - число и сумма документов за период по видам;
  - взаиморасчёты по контрагентам;
  - остатки по складам (если склад ведётся и в 1С).

  Расхождения отправляются уведомлением администратору.

### 14.3 Проверка (этап 9)

## 16. Переключение и откат

1. **Параллельная работа, 2–3 недели.**
   - 1С остаётся основной системой.
   - Каждую ночь мигратор пересобирает `vitauto_app` с копии свежего бэкапа и прогоняет сверку.
   - Ключевые пользователи повторяют в новой системе свои действия.
2. **Готовность к переключению:** гейт G11.1–G11.2, пользователи обучены, есть `docs/migration/cutover.md`.
3. **Окно переключения**, вечер пятницы:
   - (a) объявление и выход пользователей;
   - (b) полный бэкап `vitauto` (`backup-1c-full.ps1`) и выгрузка журнала регистрации;
   - (c) запрет записи в 1С для ролей АРМ, PWA в режиме «только чтение»;
   - (d) `extract` → `legacy` → `load` → `derive` → `reconcile` по замороженной базе;
   - (e) G11.3;
   - (f) PWA на `VITE_BACKEND=go`;
   - (g) включение обмена с бухгалтерией: в 1С с этого момента документы АРМ приходят только из outbox.
4. **Откат** в течение первой недели.
   - Если найдена блокирующая ошибка, PWA возвращается на `odata`, и 1С снова открывается на запись.
   - Данные, введённые в новой системе, переносятся обратно командой `migrator export-onec`. Она проверяется на копии **до** переключения.
5. **После приёмки:** 1С продолжает работать как бухгалтерия (вариант A), дампы архивируются вне сервера.

## 17. Риски

| Риск | Мера |
|---|---|
| Бизнес-логика АРМ разбросана по BSL и неявна | перенос по сценариям e2e и `docs/checks-algorithms.md`, `matrix-statuses-codes-formulas.md`; каждый алгоритм получает unit-тест с примерами из 1С |
| Номера таблиц расширения (`…X1`) меняются при переустановке расширения | карта генерируется заново перед каждым прогоном (G0.2) |
| Неполная выгрузка через OData | `legacy` строится по inventory, R1 сравнивает с прямым `COUNT(*)` по таблице хранения |
| Остатки зависят от проведения «Автосервиса» | переносятся сами движения; новые движения создают только документы нового стека; R5 каждую ночь |
| Одновременные правки | версия и `If-Match`, 409 и баннер (раздел 11) |
| Пароли не переносятся | одноразовые коды при первом входе |
| Тесты зависят от остатков сида (`m06`, `m23`) | сид `db/seed` создаёт остатки заново перед каждым прогоном |
| Обмен с 1С отклонит документ | outbox, повтор, журнал, ручная очередь, ночная сверка |
| Юридически значимые документы и ККТ | остаются в 1С (вариант A) |

## 18. Правила ветки

- Вся работа по миграции ведётся в `migration/pg-go-vue`. Исправления 1С-части (`src-xml`, `.cfe`) делаются в своей ветке АРМ и попадают сюда merge-ем, чтобы мигратор и e2e шли по актуальной логике.
- PWA меняется только аддитивно: новый бэкенд, новые экраны. Режим `odata` работает до этапа 11.
- Каждый этап — серия коммитов `MIG <N>: …` и завершающий коммит с протоколом `docs/migration/gates/stage-N.md`.
- Прод `vitauto` не используется до этапа 11; `gate.ps1` по умолчанию работает с `vitauto_dev`.
