# Покрытие процессов process.html запросами REST API АРМ (v2.9)

**Все 11 сценариев `process.html` проходят от начала до конца только запросами API** — без формы АРМ и
конфигуратора. Проверено автотестом `tools/arm-api-1c/e2e-processes.js` на тестовой базе `D:\1c\test_fresh`
(5.10.2026: 11 из 11, 401 шаг с предусловиями). Ручная проверка по шагам в PWA —
[arm-api-processes-manual-check.md](arm-api-processes-manual-check.md).

Шаги без изменения данных (уведомления M8, M11, M17/K9; «поставщик обработал» P1; получение товара N2a; розыск K8;
зарплатный фонд G5) — отмечены в прогоне, запросов не требуют.

## Что меняет статусы

| Запрос | Переход | Узлы |
|---|---|---|
| `POST /sales/imports` | лист клиента → заказ, строки «В работе» | N1, M1, G1 |
| `PATCH /lines/{id}` | поля строки по маске матрицы, статус не меняет | M2, M10, K6, K8, M15, G4, A3 … |
| `POST /lines` `view=purchases` | закупка к строке продажи (ручная, как подбор в форме) | M4 |
| отметка закупки + `POST /sales/jobs` | закупка и продажа → «Заказано», заказ поставщику | M4, M13 |
| `POST /supply/status` (supply, admin) | Заказано → Оплачено → В пути → Приёмка → На склад → Комплектуется → Собран; на «Собран» — приходная накладная | M7, P2, K1, K2, M9, K3, A3 |
| `POST /sales/shipments` | дата и номер отгрузки; строки «Готово к отгрузке», «Возврат», с партией в «В работе» | M12, M19 |
| отметка продажи + `POST /sales/jobs` | «Готово к отгрузке» → «Отгружено», расходная накладная | K5 |
| `POST /lines/transition` | переходы, которых нет в командах АРМ (таблица ниже) | M3, M9, M10, K3, N4, K1, N3, M16, M15/K7, G3, G9 |

`POST /lines/transition {view, to}` — отмеченные строки пользователя:

| to | из | роли | узлы |
|---|---|---|---|
| reserve | Новый, В работе | менеджер, админ | M3 |
| assembly | Резервирование, На склад, Приёмка | менеджер, админ | M9 |
| assembly | Готово к отгрузке | менеджер, админ, гл. механик | M10 (отклонение), G3 |
| assembly | Возврат | менеджер, админ | повторная комплектация после отказа |
| ready_to_ship | Комплектуется | кладовщик, менеджер, админ | K3 |
| shipped | Оплачено, В пути | менеджер, админ | N4 самовывоз |
| acceptance | Отгружено | кладовщик, админ | K1 после самовывоза |
| return | Отгружено, Заказано, Оплачено, В пути, На склад, Закрыт | менеджер, кладовщик, админ | N3, M16, K6 |
| closed | Отгружено (с «Документ подписан оригинал»), Готово к отгрузке, Возврат | менеджер, кладовщик, админ | M15, K7 |
| closed | Комплектуется | гл. механик, админ | G9 |

Для закупок связанная продажа (тот же ключ связи и статус) переходит вместе с закупкой. Контракт —
`openapi/arm-pwa-process.openapi.yaml`.

## Сценарии

| Сценарий | Последовательность (роль: запрос → статус) | Шагов |
|---|---|---|
| A1 Основной: закупка → отгрузка | менеджер: imports → PATCH номенклатура/кол-во/цена/поставщик → закупка + jobs → ordered; снабжение: supply/status paid → in_transit → acceptance → to_stock → assembly → assembled (ПН); менеджер: shipments → jobs (РН) → shipped → PATCH «оригинал подписан» → transition closed | 31 |
| A2 Со склада (резерв) | imports → PATCH → transition reserve → assembly; кладовщик: transition ready_to_ship; менеджер: shipments → jobs → shipped → closed | 18 (+23 пополнение) |
| A3 Смешанный заказ | строка А — как A2, строка Б — как A1; общая отгрузка обеих строк одной расходной | 42 (+23) |
| A4 Самовывоз у внешнего поставщика | … закупка → paid; менеджер: transition purchases shipped (N4); кладовщик: transition purchases acceptance (K1); менеджер: assembly; кладовщик: ready_to_ship; shipments → closed | 30 |
| B1 Виртуальный закуп | … закупка → ordered; менеджер: PATCH Количество → 403 matrix_denied (M13); админ: PATCH Количество, supply/status paid (A3) | 16 |
| B3 Контроль комплектации → снова задание | … кладовщик: ready_to_ship; менеджер: PATCH комментарий, transition assembly (M10); кладовщик: ready_to_ship; отгрузка и закрытие | 22 (+23) |
| B4 Отмена заказа у поставщика | … закупка → paid; менеджер: transition purchases return (M16) → закупка и продажа «Возврат» | 20 |
| C1 Возврат от клиента | отгрузка со склада → transition return (N3); кладовщик: комментарий (K6); shipments-корректировка (M19) | 22 (+23) |
| C2 Возврат поставщику | … закупка → to_stock; transition purchases return (M16); transition purchases closed (M15/K7) | 26 |
| C3 Отказ при получении | отгрузка → return (N3) → assembly (M10) → ready_to_ship (K3) → shipments → closed | 24 (+23) |
| E1 Поступление машины в ремонт | гл. механик: imports (G1); строка А резерв, строка Б закупка; G3 transition assembly; G4 PATCH нормо-часы; G9 transition closed | 35 |

«+23» — предусловие «товар на складе»: в базе включён контроль остатков при проведении, поэтому прогон перед
отгрузкой со склада проводит отдельную закупку до прихода и закрывает её без отгрузки.

## Что пришлось исправить или добавить

1. **Ошибка АРМ v2.8** (`Арм_ДанныеЗакупокИПродажФон`): заказу покупателя присваивалось состояние заказа поставщику —
   отгрузка «В работе» падала («новое состояние заказа "" не принадлежит виду заказа»). Теперь — «В работе» из порядка
   состояний вида заказа.
2. **`POST /lines/transition`** — переходы процессов без команды в АРМ (таблица выше).
3. **`POST /lines` для закупок** ставит «ручную правку», как подбор в форме. Без неё пересчёт остатков после прихода
   удалял закупку и создавал автоматическую строку «Черновик».
4. **`POST /sales/shipments`** — также строки «Готово к отгрузке» (M12) и «Возврат» (M19): номер отгрузки в этих
   статусах матрица вручную менять не даёт.
5. **Seed:** номенклатура и контрагенты создавались без значений, которые ставит форма УНФ (тип, направление
   деятельности, склад, счета учёта, ставка НДС, счета расчётов) — приходные и расходные накладные не проводились.
   `seed-1c.ps1` теперь заполняет их у новых и дозаполняет у созданных ранее.
6. **Пользователи API** `arm.admin`, `arm.mechanic` — для сценариев B1 и E1.

## Ограничения

- Поля УПД (K1: дата и номер УПД) в регистре АРМ отсутствуют — в API всегда пустые.
- `POST /sales/supplier-orders` — 501: команда «Заказать» в форме — заглушка; заказ поставщику создаёт «В работе».
- Нет отдельных объектов заказ-наряда: G1 — заказ покупателя, загруженный главным механиком.
- Рабочая база получит изменения после `tools/arm-api-1c/deploy-prod.ps1` и `seed-1c.ps1` (см. README).
