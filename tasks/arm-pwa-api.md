# Задача: HTTP API АРМ для PWA

## Цель

Поставить перед базой 1С HTTP-сервис, через который веб-приложение (PWA) выполняет действия АРМ: список строк, правка ячеек по матрице, команды формы продаж и канбан снабжения. Контракт уже описан, его не переписывать по ходу реализации.

**Контракт:** [openapi/arm-pwa.openapi.yaml](../openapi/arm-pwa.openapi.yaml) (OpenAPI 3.0.3, 29 операций).

HTTP-сервиса в расширении сейчас нет. Формы `АС_АРМ2` остаются для тонкого клиента; PWA ходит только в этот API.

## Источники

| Что | Где |
|---|---|
| Контракт PWA | `openapi/arm-pwa.openapi.yaml` |
| Форма продаж | `Обработка.АС_АРМ2.Форма.Форма` |
| Форма снабжения | `Обработка.АС_АРМ2.Форма.ФормаСнабжение` |
| Строки | регистр `Арм_ДанныеЗакупокИПродаж` |
| Роль интерфейса | регистр `Арм_ПраваПользователей`, перечисление `Арм_РолиИнтерфейса` |
| Право на ячейку | `Арм_ОбщегоНазначенияАРМ.МожноРедактироватьПолеАРМ`, `ИмяФормыАРМПоРоли` |
| Матрица | `default-matrix.js`, уровень «Заказ» |

Расширение для реализации — актуальная версия рядом со скриптом (`АРМЗакупокИПродаж_v2.7` на момент постановки). Новую версию расширения завести отдельно, v2.7 не переписывать поверх.

## Границы задачи

**Входит:**

- сессия: вход пользователем информационной базы, роль из регистра, экран `sales` или `supply`;
- чтение колонок матрицы с маской прав `+` / `c` / `.`;
- списки `sales`, `purchases`, `supply` с отборами периода, скрытия отгруженных и вычеркнутых, «только с закупками», группировки и отбора по заказу покупателя;
- запись одного поля строки с теми же проверками, что ячейка в форме (роль, статус, автор для режима «создатель», замок фона);
- пересчёт суммы себестоимости, цены продажи и коэффициента после записи;
- отметка строки и «выделить все строки заказа», итоги выделения;
- подбор номенклатуры в продажи и закупки;
- команды продаж: «В работе» (фон и повтор с подтверждением сплита), «Подготовлено», создать и провести заказ покупателя, удалить заказ, создать заказ поставщику, дата и номер отгрузки, загрузка листа покупателя;
- канбан снабжения: оплачено, в пути, приёмка, на склад, комплектация, собран (с датой частичного прихода);
- справочники для полей выбора: контрагент, договор только этого контрагента, номенклатура, партия, вид услуги, форма оплаты;
- карточка документа, который форма открывает из строки;
- коды ошибок из схемы: `matrix_denied`, `field_readonly`, `row_locked`, `not_author`, `unfinished_purchase`, `nothing_marked`, `need_split`, `contract_owner`.

**Не входит:**

- сам фронтенд PWA (манифест, офлайн, вёрстка);
- публикация базы на веб-сервере 1С и сертификаты — только контракт и сервис, публикацию описывает отдельная заметка в задаче, если без неё сервис нельзя вызвать;
- смена прав матрицы и новые колонки;
- правила автозаполнения `fieldRules` (госномер подтягивает машину, «одно из трёх» по номенклатуре), кроме отбора договора по заказчику — он уже в `GET /directories/contracts`;
- замена форм тонкого клиента.

## Что сделать

1. **Сервис.** HTTP-сервис расширения с корнем `/api/arm/v1`. Операции и тела — как в OpenAPI, имена путей не менять.
2. **Сессия.** `POST /session` проверяет пользователя ИБ. Дальше запросы идут с токеном. `GET /session` возвращает роль и экран: снабжение → `supply`, остальные роли матрицы → `sales`. Пользователь без записи в регистре — менеджер, как в форме.
3. **Строки.** Чтение и `PATCH` одного поля через тот же регистр, что форма. Поле, которого нет в регистре, не записывать (`field_readonly`). Договор проверять на владельца-заказчика (`contract_owner`).
4. **Команды.** Каждая операция из разделов `sales`, `supply`, `jobs` вызывает уже существующую логику форм, а не вторую реализацию статуса. «В работе» возвращает `202` и задание; `GET /jobs/{id}` отдаёт `running`, `need_split`, `done` или `failed`.
5. **Права.** Сервер не доверяет маске, которую PWA получила в `GET /matrix`. Запись и команда проверяются на сервере ещё раз.

## Проверка

На копии базы с расширением, пользователь `arm.manager` / пароль `1` (и по одному запросу под `arm.storekeeper` и `arm.supply`).

1. `POST /session` под менеджером возвращает `screen=sales`. Под `arm.supply` — `screen=supply`.
2. `GET /lines?view=sales` отдаёт строки seed. `view=supply` менеджеру отвечает `403`.
3. `PATCH` поля, которое матрица разрешает менеджеру в статусе строки, сохраняется и читается обратно. Поле с маской `.` в этом статусе — `403` `matrix_denied`. Артикул номенклатуры — `403` `field_readonly`.
4. «Подготовлено» по строке с незавершённой закупкой — `409` `unfinished_purchase`.
5. «В работе» по отмеченным строкам возвращает задание; повторный опрос доходит до `done` или `need_split`.
6. Снабжение переводит отмеченную закупку в «На складе»; строка в списке `view=supply` в этом статусе.
7. Файл OpenAPI и реализованные пути совпадают: нет лишних путей и нет пути из файла без обработчика.
