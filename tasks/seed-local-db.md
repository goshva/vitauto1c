# Seed локальной базы: способы наполнения в контексте матрицы и процессов

Ветка `seed-data`. Анализ от 01.10.2026: исходники `АРМЗакупокИПродаж_v2.3`, `index.html`, `process.html`, `column-matrix (5).json`. Часть выводов проверена на копии базы `D:\1c\test_v21`; в ней v2.1, но обработчики документов те же.

## Зачем seed

База «Автосервис» почти пустая: 2 служебных контрагента, 0 договоров, регистр АРМ `Арм_ДанныеЗакупокИПродаж` пуст. Без данных нельзя:

- **проверять матрицу** — «роль × статус × колонка»: нужны строки в каждом из 12 статусов и пользователи на каждую роль;
- **проверять процессы** — 11 сценариев `process.html`: нужны заказы, которые проходят шаги сценария;
- **принимать задачи** — например, отбор договоров по заказчику требует контрагентов с договорами.

## Что нужно наполнить

| Слой | Что | Источник значений | Для чего |
|---|---|---|---|
| 0. НСИ | Контрагенты и договоры, номенклатура, партии и остатки, виды услуг, формы оплаты | `DIRECTORIES` в `index.html`: 4 контрагента, 5 договоров, 5 позиций, 4 машины, 5 агрегатов | Всё остальное |
| 1. Пользователи и роли | Пользователь на каждую роль матрицы, запись в `Арм_ПраваПользователей` | 6 ролей матрицы | Матрица |
| 2. Заявки | Заказы покупателей со строками клиента (артикул, наименование, количество, ГРЗ, территория, срочность) | `SAMPLE_ROWS` в `index.html`, шаги N1/M1 в `process.html` | Строки АРМ в начальном статусе |
| 3. Поля матрицы без логики | Марка, модель, агрегат, госномер, VIN, двигатель, РРЦ, «Оплачено» и т. п. | `SAMPLE_ROWS`, `vehicles` | Отображение и правка колонок (v2.1+) |
| 4. Статусы | Строки в каждом статусе | 12 статусов матрицы | Матрица |
| 5. Цепочки документов | Заказ поставщику, приходная накладная, отгрузка | Сценарии `process.html` | Процессы |

## Что выяснено проверкой

1. **Строки попадают в АРМ через документ, а не прямой записью в регистр.** Форма загрузки (`ФормаЗагрузкиДанных`) создаёт «Заказ покупателя» с полями клиента в табличной части «Запасы». Обработчик расширения `Арм_ПриЗаписи` сам заполняет регистр (`ОбновитьДанныеПоОбъекту`): статус «В работе», вид операции «Продажа», заказчик, договор, номер заказа.
2. **Тот же путь работает через COM.** На копии базы заказ, созданный скриптом, дал 2 строки в регистре без единой прямой записи. Экспортные функции общих модулей расширения из COM доступны: проверен вызов `Арм_ОбщегоНазначенияАРМ.НайтиДоговор`.
3. **Блокер: расширение подключено в безопасном режиме — в обеих базах, включая рабочую.** В этом режиме платформа отключает расширения модулей основной конфигурации. В журнале: «расширение модуля Документ.ЗаказПокупателя запрещено… подключено в безопасном режиме». Заказы в АРМ не попадают. На копии режим отключён через `ConfigurationExtensions`, после этого всё заработало. В рабочей базе режим не менялся. Причина: `install-1c.ps1` загружает расширение командой `/LoadCfg -Extension`, а она включает безопасный режим по умолчанию.
4. **Контрагент создаётся одной записью**, и база сама находит для него «Основной договор». Отдельный договор с одним наименованием не записывается: не хватает обязательных реквизитов (организация, вид договора и т. п.). Их нужно выяснить.
5. **COM-соединитель требует регистрации библиотеки типов** (`comcntr.dll`) и 32-битного процесса. Из PowerShell (.NET) вложенные объекты 1С не вызываются, из 32-битного `cscript` (JScript) всё работает.

## Несовпадения модели, которые seed должен учитывать

**Статусы: в матрице 12, в АРМ (`Арм_СтатусыАРМ`) — 15, и они не совпадают.** Соответствие ниже — предположение, его нужно подтвердить:

| Статус матрицы | Статус АРМ | Замечание |
|---|---|---|
| Новый | Черновик / ВРаботе | документ создаёт строки сразу в «В работе» |
| Заказано у поставщика | Заказано, ЧастичноЗаказано | |
| Оплачено | Оплачено | |
| В пути | ТоварВПути | |
| Ожидаем поступление | — | в АРМ нет |
| Приемка | Приходуется | |
| Резервирование | НаСкладе | неточно |
| Комплектация | Комплектуется | |
| Готово к отгрузке | Собран / Подготовлено | |
| Отгружено | Отгружено | |
| Возврат | — | в АРМ нет |
| Закрыт | Завершено / Выполнено | |

**Роли: в матрице 6, в АРМ (`Арм_РолиИнтерфейса`) — 3:** Менеджер, Снабжение, Администратор. Кладовщика, главного механика, клиента в АРМ нет; «Снабжение» — это не «Поставщик (внешний портал)».

**Справочника машин нет.** Марка, модель, госномер, VIN, двигатель хранятся строками в регистре (v2.1). Автозаполнение по госномеру seed не обеспечит.

**Уровни «Заказ» и «Деталь»** в АРМ не разделены: статус хранится в строке.

## Способы

| № | Способ | Как работает | Плюсы | Минусы | Для слоёв |
|---|---|---|---|---|---|
| 1 | **COM-скрипт + данные в JSON** | `seed/data.json` в репозитории, запуск `seed-1c.ps1` → 32-битный `cscript`: справочники и документы создаются через менеджеры 1С | Проверен на копии; данные читаемы и версионируются; повторный запуск безопасен (поиск по наименованию); срабатывает логика расширения; встраивается в `install-1c.ps1` | Нужны регистрация `comcntr` и 32 бита; код на JScript; обязательные реквизиты объектов УНФ надо выяснять | 0–4, частично 5 |
| 2 | **Отдельное расширение `АРМ_Seed.cfe`** | Общий модуль на встроенном языке с процедурой `Заполнить()`; ставится только на базы разработки; запуск командой в АРМ или одной строкой через COM | Код на языке 1С рядом с логикой АРМ; можно вызывать служебные процедуры расширения; на рабочую базу не попадает | Нужно собрать новое расширение с нуля (в конфигураторе или v8unpack); ещё один артефакт | 0–5 |
| 3 | **Внешняя обработка `.epf`** | Запуск `1cv8 ENTERPRISE /Execute seed.epf` | Не меняет расширение; привычно для 1С | Нужен формат исходников `.epf`; старт УНФ с диалогами; хуже автоматизируется | 0–5 |
| 4 | **Штатная загрузка заявки** | Форма `ФормаЗагрузкиДанных`: вставка таблицы «Номер, Дата, Срочность, ГРЗ, Территория, Артикул, Наименование, Ед. изм., Количество» | Точно повторяет шаги N1/M1; ничего не писать — нужны только файлы-образцы | Вручную; только слой 2: НСИ, роли и статусы не покрывает | 2 |
| 5 | **Образ базы** | После seed сохранить `.dt` или копию `1Cv8.1CD`; `install-1c.ps1 -SeedDt` восстанавливает | Сброс к эталону за секунды; идеальная основа для автопроверок | Около 2 ГБ, не для git; устаревает при смене версии расширения — нужен пересбор способом 1 или 2 | Все, как кэш |
| 6 | **Сценарии интерфейса (Vanessa Automation)** | Сценарий проходит шаги процесса в интерфейсе | Данные полностью согласованы; заодно это тесты процессов | Самый дорогой способ; нужна настройка тест-клиента | 5 |

Прямую запись строк в регистр как основной способ не рекомендую: строки без документа расходятся с логикой АРМ (заказы поставщикам, пересчёт партий, фоновое задание). Она допустима только для слоёв 3 и 4: поля без логики и принудительная установка статуса.

## Рекомендация

Сочетать способы 1, 5 и позже 6, в три шага.

1. **Матричный seed (способ 1).** Данные из `DIRECTORIES` и `SAMPLE_ROWS`: контрагенты, номенклатура, по одному пользователю на роль АРМ, 3–4 заказа покупателей через документ. Новые поля матрицы — прямой записью. Статусы — принудительной установкой `СтатусСтроки`, чтобы в таблице были строки во всех статусах, у которых есть соответствие в АРМ. Этого достаточно для проверки матрицы и приёмки текущих задач.
2. **Образ (способ 5).** Результат шага 1 сохранить как эталонную копию для быстрого сброса и автопроверок.
3. **Процессный seed (способ 6 или вызовы процедур расширения через способ 1 или 2).** Сценарии `happy`, `stock`, `mixed_order` из `process.html`: статусы меняются реальными операциями АРМ (заказ поставщику, приход, комплектация), а не установкой поля.

Перед шагом 1 нужно:

- **отключать безопасный режим расширения** при установке (доработка `install-1c.ps1` и `install-1c-pgsql.ps1`) — без этого seed через документы не работает, как и сам АРМ;
- согласовать таблицу соответствия статусов и решить, что делать с ролями, которых нет в АРМ;
- выяснить обязательные реквизиты договора, номенклатуры и партии в УНФ.

## Предлагаемый состав ветки

```
seed/
  data.json        # НСИ, пользователи и роли, заказы, статусы — из index.html
  seed.js          # запись в базу через COM (32-битный cscript)
seed-1c.ps1        # запуск: проверка базы, регистрация comcntr, безопасный режим, seed.js, отчёт
tasks/seed-local-db.md
```

## Вопросы к постановщику

1. Соответствие 12 статусов матрицы и 15 статусов АРМ — верна ли таблица выше? Что с «Ожидаем поступление» и «Возврат»?
2. Роли кладовщика, главного механика, клиента и поставщика: заводить в `Арм_РолиИнтерфейса` сейчас или seed ограничивается тремя существующими?
3. Отключать безопасный режим расширения в рабочей базе? Сейчас обработчики расширения на документах там не работают.
4. Seed нужен только для копий и баз разработки, или демо-данные допустимы и в рабочей базе до запуска?

## Решения постановщика (01.10.2026)

1. **Статусы.** «Ожидаем поступление» и «Возврат» есть в матрице, но их нет в АРМ. Seed ставит строки в 10 статусов матрицы, у которых есть пара в АРМ. Соответствие хранится в `seed/data.json` (`statusMap`) и правится без кода. Добавлять ли два недостающих статуса в АРМ — не решено.
2. **Роли.** Кладовщик, главный механик, клиент и поставщик заведены в `Арм_РолиИнтерфейса` сразу — версия расширения v2.4.
3. **Безопасный режим.** Отключается на время заполнения и возвращается после него.
4. **Где нужен seed.** Везде: скрипт работает с любой базой, включая рабочую.

## Реализация — шаг 1 (матричный seed)

- **`АРМЗакупокИПродаж_v2.4.cfe`** (исходники `src/АРМЗакупокИПродаж_v2.4`): четыре новых значения в `Арм_РолиИнтерфейса`; новые роли открывают форму продаж. Права по колонкам и статусам для них — отдельные задачи.
- **`seed/data.json`** — данные из `index.html`: 5 контрагентов с 5 договорами, 5 позиций номенклатуры, 4 машины, виды услуг и формы оплаты, 7 пользователей с ролями, 4 заказа покупателей (номера клиента `SEED-*`) с 11 строками в 10 статусах.
- **`seed/seed.js`** — запись в базу через COM. Заказы создаются документом, регистр заполняет расширение; затем в строки дописываются статус, номенклатура, цены и поля матрицы.
- **`seed-1c.ps1`** — запуск: проверяет COM-соединитель, при необходимости регистрирует библиотеку типов, отключает безопасный режим, запускает наполнение, возвращает режим.

```powershell
.\seed-1c.ps1                        # база из 1c-env.json или C:\1c_bases\autoservice
.\seed-1c.ps1 -IbDir D:\1c\test_seed
.\seed-1c.ps1 -KeepSafeModeOff       # не возвращать безопасный режим
```

**Проверено на чистой копии рабочей базы (`D:\1c\test_seed`):**

- v2.4 загружена и применена, `CheckCanApplyConfigurationExtensions` — код 0, `CheckModules` (сервер, тонкий клиент) — код 0;
- первый запуск: создано 29 объектов, 11 строк АРМ — по одной в статусах «На складе», «Отгружено», «Завершено», «Заказано», «Оплачено», «Товар в пути», «Приходуется», «Комплектуется», «Собран» и две в «Черновик»;
- повторный запуск: создано 0, уже было 32, строк по-прежнему 11;
- безопасный режим был включён, после заполнения включён обратно.

**Что нужно знать:**

- Договоры записываются в режиме загрузки: обычная запись договора в УНФ через COM не проходит («Не удалось записать»), причина не выяснена. Отсюда 5 предупреждений при первом запуске.
- УНФ сама создаёт каждому контрагенту «Основной договор». Поэтому у «Частного клиента» договор есть, хотя в прототипе его нет. Для проверки «у заказчика нет договоров» этот договор нужно пометить на удаление.
- Пользователи seed — элементы справочника с ролью АРМ, без учётных записей для входа. Войти под ролью пока можно только под «Админ». Учётные записи — отдельное решение: для них нужны пароли и роли 1С.
- После возврата безопасного режима новые заказы в АРМ не попадают — так работает сам АРМ в этом режиме.
- Процессные данные (заказы поставщикам, приходы, отгрузки) не создаются: статусы выставлены принудительно. Это шаг 3 рекомендации.

### Исправление после запуска на свежеустановленной базе (01.10.2026)

На только что установленной базе запись расширения с отключённым безопасным режимом прервалась предупреждением 1С «Предупреждение безопасности… Разрешить открывать данный файл?» — через COM на него ответить нельзя. `cscript` при этом вернул код 0, скрипт запуска принял это за «режим уже отключён», и заказы создались без строк АРМ.

Что изменено:

- результат отключения читается из отчёта и перепроверяется отдельным сеансом; если режим не отключён, наполнение не запускается;
- если запись упирается в защиту от опасных действий, скрипт снимает её у расширения и у текущего пользователя ИБ и повторяет запись — об этом пишет предупреждение;
- заказы `SEED-*`, созданные без строк АРМ, при повторном запуске восстанавливаются: дозаполняются ключи строк и вызывается штатное `ОбновитьДанныеПоОбъекту`.

Проверено на копии этой базы (`D:\1c\test_fresh`): 4 заказа восстановлены, 11 строк в 10 статусах. Само предупреждение на копии не воспроизвелось, поэтому ветка со снятием защиты в работе не проверена.

> Соответствие статусов обновлено 01.10.2026 по ответам постановщика: статусов матрицы теперь 15, seed покрывает 13. Актуальная таблица — в [matrix-statuses-codes-formulas.md](matrix-statuses-codes-formulas.md).
