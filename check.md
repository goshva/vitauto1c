# Как проверить работу (для пользователя)

Документ описывает, **что уже работает**, и даёт пошаговые кейсы проверки.
Адрес стенда: **http://127.0.0.1:18180/** (или тот, который сообщил администратор).

---

## 0. Общие правила проверки

1. **Обновите страницу** после каждого обновления сборки — **Ctrl+F5**
   (service worker кеширует старый бандл, иначе можно проверять старое).
2. Вход: пользователь **«Администратор»**, пароль **`admin123`**
   (роли менеджера, снабжения, кладовщика и т.д. — по учётным записям стенда).
3. Если экран «пустой» или кнопки не реагируют — проверьте, что вы вошли
   под нужной ролью: часть разделов видна только администратору.
4. Все проверки ниже — **только чтение и безопасные действия**.
   Там, где действие меняет данные, это указано отдельно; в конце кейса — как откатить.
5. Если что-то не совпало с ожиданием — запишите: роль, раздел, что нажали,
   что увидели, что ожидали. Это ускорит разбор.

## 1. Что реализовано и как это проверить

### 1.1. Настройки прав — матрица прав по статусам

**Где:** меню → «Настройки прав» → вкладки групп → «Матрица прав по статусам».

**Что проверить:**

| Шаг | Действие | Ожидаемо |
|---|---|---|
| 1 | Открыть «Настройки прав» под админом | Список 7 групп, вкладки, матрица |
| 2 | Выбрать группу «Администратор» | Таблица «колонка × статус», ячейки `+`, `c`, `.` |
| 3 | Нажать на ячейку | Символ меняется по кругу: `.` → `+` → `c` → `.` |
| 4 | Изменить несколько ячеек | Появляется «Есть несохранённые правки» и кнопки «Сохранить матрицу» / «Отменить» |
| 5 | Нажать «Сохранить матрицу» | Тост «Матрица сохранена», счётчик правок исчезает |
| 6 | Обновить страницу (F5) | Изменения на месте (сохранились в `matrix.json`) |
| 7 | Войти не-админом (например, «Менеджер») | «Режим просмотра», ячейки не кликаются |

**Что означает ячейка:** `+` — можно менять, `c` — только автор строки,
`.` — нельзя. Изменения применяются сразу, **без пересборки**.

**Откат:** верните ячейки в исходное положение и снова «Сохранить матрицу».

### 1.2. Управление процессами

**Где:** меню → «Процессы» (видно **только админу**).

**Что проверить:**

| Шаг | Действие | Ожидаемо |
|---|---|---|
| 1 | Открыть раздел под админом | Заголовок «Управление процессами», правила применения изменений |
| 2 | Прочитать правила | «Не влияют на незавершённые», «могут наследоваться», «начинаются только с первого узла», «не затрагивают начатое» |
| 3 | Открыть вкладку «Процесс заявки» | Схема процесса, узлы, дорожки, статистика |
| 4 | Открыть вкладку «Редактирование процесса» | Таблица узлов: роль, название, покрытие, ТЗ, код АРМ, «со схемы» |
| 5 | Изменить название узла и нажать «Сохранить» | Тост «Сохранено», дорожки перерисовались, значение осталось после F5 |
| 6 | «+ Узел» | Появляется новый узел, статистика обновилась |
| 7 | «Сбросить к исходному» | Узлы вернулись к исходным, счётчик совпал с исходным |
| 8 | «Экспорт JSON» / «Импорт JSON» | Файл скачивается / узлы загружаются из файла |

**Важно:** правки хранятся **в браузере** (`localStorage`) и на сервер не уходят.
Чтобы вернуть исходное состояние — «Сбросить к исходному» или очистить данные сайта.

### 1.3. Запрет удаления строки и заказа (п. 15)

**Где:** список строк (продажи/закупки) → строка → «Действия» / меню строки;
удаление заказа целиком — в листе строки → «Удалить заказ».

**Что проверить:**

| Шаг | Действие | Ожидаемо |
|---|---|---|
| 1 | Войти менеджером, открыть «Продажи» | В меню строки пункта «Вычеркнуть» **нет**, «Удалить заказ» **нет** |
| 2 | Войти админом | Пункты «Вычеркнуть» и «Удалить заказ» **есть** |
| 3 | Под админом вычеркнуть строку | Тост «Строка вычеркнута», строка помечена |
| 4 | Попробовать то же менеджером через консоль API | `DELETE /lines/{id}` → **403** «Вычеркнуть строку может только администратор» |
| 5 | Попробовать удалить заказ менеджером | `DELETE /sales/customer-orders/{id}` → **403** «Удалить заказ может только администратор» |
| 6 | То же под админом (заказ без строк дальше «В работе») | **204**, заказ и его строки помечены удалёнными |

**Аудит удаления (кто и когда):** каждое удаление — мягкое (пометка), записываются
`deleted_by_id` (кто) и `deleted_at` (когда); восстановление их очищает.
Проверка в БД: `select deleted, deleted_by_id, deleted_at from doc.customer_order where id = '…'`
и то же по `arm.line`. Покрыты: строки, заказы, справочники, каталог, бренды, вложения.

**Откат:** под админом вернуть строку/справочник (восстановление в карточке).

## 2. Проверка через консоль API (если нужно точнее)

Меню → «Консоль API» (только админ). Можно выполнять запросы вручную:

```
GET  /health
GET  /matrix
GET  /settings/groups
GET  /catalog/goods
GET  /unidentified
GET  /returns
```

Тело запроса — JSON, метод выбирается из списка. Ответ показывается как есть
(код, заголовки, тело). Это удобно для проверки прав: под разными ролями
выполняйте один и тот же запрос и сравнивайте коды (`200`, `403`, `404`).

## 3. П. 4 — «Колонки движения» (5 колонок + автопростановка)

**Что это:** в списке строк — 5 отдельных колонок движения, а не один общий статус:

| Колонка | Поле в строке | Что показывает |
|---|---|---|
| Резерв | `reserve_qty` | сколько зарезервировано на складе |
| Оплата | `paid_status` | статус оплаты |
| Приёмка | `receipt_date` | дата приёмки (приход) |
| Отгрузка | `shipment_date` | дата отгрузки |
| Возврат | `line_status` | статус строки, включая «Возврат» |

**Где включить набор «Колонки движения»:** список строк → кнопка «Колонки»
(настройка полей) → в списке режимов выбрать этап **«Колонки движения»**
(группа «Движение»). Набор: `Резерв / Оплата / Приёмка / Отгрузка / Возврат`.
В «Основных» (наборе по умолчанию) эти колонки тоже включены: «Резерв», «Оплата»,
«Дата приёмки», «Дата отгрузки», а «Статус строки» показывается всегда.

**Как проверить:**

| Шаг | Действие | Ожидаемо |
|---|---|---|
| 1 | Открыть «Продажи» | В списке видны колонки движения: «Резерв», «Оплата», «Дата приёмки», «Дата отгрузки», «Статус строки» |
| 2 | «Колонки» → этап «Колонки движения» (группа «Движение») | Остаются ровно 5 колонок: Резерв / Оплата / Приёмка / Отгрузка / Возврат |
| 3 | Создать отгрузку по заказу (действие «Отгрузка») | У строк проставляется «Дата отгрузки» |
| 4 | Провести приёмку (снабжение → «Собран») | У строк проставляется «Дата приёмки» |
| 5 | Провести возврат («Возвраты» → «Провести») | У строк «Статус строки» = «Возврат» |
| 6 | Проверить резерв и оплату | «Резерв» = зарезервированное количество (пересчитывается); «Оплата» — по факту |

**Автопростановка:** даты и статус проставляются при проведении документов
(отгрузка → дата отгрузки, приёмка → дата приёмки, возврат → статус «Возврат»);
«Оплата» и «Резерв» — по факту оплаты/резерва. Изменения применяются к строке
сразу после проведения.

**Где посмотреть этап процесса:** меню → «Процессы» (админ) → узел
**«Колонки движения»** (роль «Движение»), и в `process.html` — тот же узел.

## 3.1. П. 11 — «Резервировать доступное» (частичный резерв и дозаказ)

**Где:** список «Продажи» → отметить строки → «Действия» → блок **«Резерв»** →
**«Резервировать доступное»** (можно выбрать зону склада).

**Что делает:** свободный остаток партий распределяется FIFO по отмеченным продажам:
доступное количество уходит в **резерв** (статус «Резервирование», колонка «Резерв»),
недостающее — в черновую строку закупки **«к дозаказу»**. Резерв может быть частичным.

**Как проверить:**

| Шаг | Действие | Ожидаемо |
|---|---|---|
| 1 | «Продажи» → отметить строку (Черновик / В работе) | «Действия» → блок «Резерв» |
| 2 | «Резервировать доступное» → «Зарезервировать» | Тост «в резерв N, к дозаказу M, закупок K» |
| 3 | Посмотреть строку | Есть остаток: статус «Резервирование», «Резерв» = доступное количество; нет остатка: появилась строка «к дозаказу» (Черновик, список «Закупки») |
| 4 | Отметки | После команды снимаются |
| 5 | Повторить кладовщиком | **403** — команда менеджеру и администратору |

**Почему может уйти всё в дозаказ:** остаток берётся из движений склада (`stock.move`) и
распределяется FIFO по всем открытым строкам номенклатуры, а не только по отмеченным.
В демо-данных движения по партиям создаёт `seed/demo-data.sql`
(«Демо-остаток для резерва»); если остаток уже разобран более ранними строками,
отмеченная строка законно уходит в дозаказ.

**API:** `POST /lines/reserve-available` с `{"view":"sales","zoneId":"…"}` →
`{processed, total, reserved, shortage, purchases}`.

## 3.2. П. 12 — «Варианты поставки»

**Где:** открыть строку (лист деталей) → в ряду действий **«Варианты поставки»**
(доступно менеджеру, снабжению и администратору).

**Что это:** список поставщиков по номенклатуре строки с ценой и сроком —
сохранённые предложения и подсказки **из истории закупок** («у кого и по какой цене брали»).
Выбор варианта проставляет в строку поставщика, цену и срок; вариант запоминается.

**Как проверить:**

| Шаг | Действие | Ожидаемо |
|---|---|---|
| 1 | Лист строки → «Варианты поставки» | Список вариантов: поставщик, цена, срок; у исторических — пометка «из истории закупок (N)» |
| 2 | Нажать «Выбрать» у варианта | Тост «Вариант выбран: …», строка получила поставщика, цену и срок; у варианта метка «выбран» |
| 3 | «Выбрать поставщика» → найти → указать цену и срок → «Сохранить» | Вариант добавлен в список и сохранён |
| 4 | Обновить страницу (F5) | Сохранённые варианты и выбранный поставщик на месте |
| 5 | Открыть кладовщиком | Пункта «Варианты поставки» нет; через консоль API → **403** |

**API:** `GET /lines/{id}/supply-options`, `POST /lines/{id}/supply-options`
(`{supplierId, price, deliveryTerm, comment}`), `POST /lines/{id}/supply-options/{id}/apply`
(идентификатор варианта или `history:<supplierId>`).

## 4. П. 2 — «Сопоставление номенклатуры» (неопознанные позиции)

**Что это:** отдельное рабочее место для позиций, которые пришли на склад,
но не опознаны (нет в номенклатуре или не совпали по артикулу).
Кладовщик создаёт «неопознанную» позицию, менеджер привязывает её к номенклатуре
или отмечает «найдено».

**Экран:** меню → **«Неопознанные»** (пункт виден всем ролям, API — авторизованный).
Позиции приходят из строк заказов, со склада и из цеха; кладовщик фиксирует факт,
менеджер привязывает к номенклатуре или отмечает «найдено».

**API:** `GET/POST /unidentified`, `GET /unidentified/{id}`,
`POST /unidentified/{id}/link`, `POST /unidentified/{id}/found`.

**Как проверить:**

| Шаг | Действие | Ожидаемо |
|---|---|---|
| 1 | Меню → «Неопознанные» | Список: факт-наименование, артикул, количество, источник, дата; сверху «Не разобрано: N из M» |
| 2 | «Создать» → ввести факт-наименование и артикул → «Создать» | Тост «Неопознанная позиция создана», позиция появилась в списке со статусом «не разобрано» |
| 3 | Выбрать позицию → «Привязать к номенклатуре» → ввести название/артикул товара → «Найти» | Список товаров с артикулом и кодом поставщика |
| 4 | Нажать «Привязать» у нужного товара | Тост «Привязано к «…»», статус позиции → «привязано» |
| 5 | Выбрать другую позицию → «Найдено» | Тост «Отмечено как найдено», статус → «найдено» |
| 6 | Обновить страницу (F5) | Список и статусы сохранились |
| 7 | Поиск вверху списка | Фильтр по факт-наименованию и артикулу |

**Проверка через API** (для точности): `GET /api/v1/unidentified` → `200` и массив
позиций; `POST /api/v1/unidentified` с `{"factName":"…"}` → `201`;
`POST /api/v1/unidentified/{id}/link` с `{"nomenclatureId":"…"}` → `204`.

## 6. Если что-то сломалось

1. **Ctrl+F5** — почти всегда решает проблему со старым бандлом.
2. Проверьте `GET /health` в консоли API — должно быть `{"database":"ok","status":"ok"}`.
3. Посмотрите «Журнал запросов» (меню → «Журнал») — там видно, какие запросы
   ушли и какие коды вернулись.
4. Если ошибка повторяется — пришлите: роль, раздел, действие, текст ошибки
   и время. По журналу это легко найти.
