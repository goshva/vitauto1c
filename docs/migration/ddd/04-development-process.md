# 4. Порядок разработки: пошаговая проверка процесса написания и тесты

Каждая функция нового стека пишется от узла процесса к коду, сверху вниз. Каждый шаг закрывается проверкой, и пока проверка не прошла, следующий шаг не начинается. Проверки автоматизированы, ручные отмечаются в протоколе гейта.

## 4.1 Шаги для одного узла (или сценария)

| № | Шаг | Что пишется | Проверка шага (должна пройти) |
|---|---|---|---|
| 1 | **Модель** | узел есть в process.html; `extract-domain.mjs` обновил `domain-model.json` | `node --test tools/migration/tests/` — модель актуальна (тест «domain-model совпадает с источниками») |
| 2 | **Сопоставление** | запись узла в `node-map.json`: контекст, агрегат, команда, API, события, уведомления, этап, тесты | тест «каждый узел сопоставлен», «события объявлены», «контекст и агрегат существуют» |
| 3 | **Документы** | `ddd-gen.mjs` — схемы, трассировка, каталог тестов | тест «generated/* совпадает с render()»; в `fsm.md` нет «НЕТ» |
| 4 | **Контракт** | операция в `api/openapi.yaml` (и событие в `asyncapi.yaml`), пример запроса и ответа | `spectral lint` = 0; тест паритета маршрутов; `task gen` без изменений (G1.2, G1.3, G1.5) |
| 5 | **Тесты до кода** | Go-тест `T-<узел>` (приёмочный, по каталогу) и случаи матрицы `M-<роль>` для колонок узла; e2e-шаг сценария `S-<сценарий>` | тесты компилируются и **падают** (красные) — фиксируется в PR |
| 6 | **Схема БД** | goose-миграция при необходимости; `COMMENT ON` | `goose up` на чистой базе; G2.4 (комментарии у всех столбцов) |
| 7 | **Домен** | команда агрегата + `authorize` + событие | unit-тесты агрегата зелёные; покрытие пакета ≥ 80 % |
| 8 | **API** | обработчик (сгенерированный интерфейс oapi-codegen) | `go test ./...` с проверкой ответов по схеме OpenAPI |
| 9 | **Политики и WS** | реакция на событие, уведомление, событие WebSocket | тест политики; e2e r01 для экрана узла |
| 10 | **PWA** | экран использует `src/http/backend.js`; кнопки по матрице | `vitest`; e2e `S-<сценарий>` на Go-бэкенде |
| 11 | **Паритет с 1С** | тот же сценарий на OData-бэкенде | e2e на обоих бэкендах даёт одинаковый результат (G4.2 / G5.3) |
| 12 | **Гейт** | `gate.ps1 -Stage N` | код 0; протокол `docs/migration/gates/stage-N.md` с ручной отметкой |

**Правило коммитов.** Шаги 1–5 — отдельный коммит «MIG N: spec <узел>», шаги 6–11 — «MIG N: impl <узел>». В PR видно, что тесты появились раньше кода и сначала падали.

## 4.3 Готовность узла (Definition of Done)

Узел готов, когда выполнено всё:
- **трассировка:** в [generated/nodes.md](generated/nodes.md) у узла заполнены контекст, команда, API и тесты, а этап совпадает с текущим;
- **тесты:** `T-<узел>` зелёный; случаи матрицы для колонок узла зелёные; e2e-сценарии, где есть узел, зелёные на Go и не хуже 1С;
- **реальное время:** событие узла приходит другим ролям, видно в e2e r01;
- **матрица:** узла нет в «Наблюдениях» [processes.md](generated/processes.md) либо решение заказчика записано в `node-map.json`.

## 4.4 Как проверяется сам процесс написания

Автоматически, на каждом коммите (CI) и в гейте этапа:
- **актуальность модели:** изменили `index.html`, `process.html` или матрицу и не перегенерировали модель — тест падает;
- **полнота документов:** узел без сопоставления, сценарий без схемы, роль без раздела, переход без покрытия, событие без объявления — тест падает;
- **ТЗ и план:** в ТЗ нет требования на контекст, узел или проверку — тест падает (`tz.test.mjs`);
- **данные:** непустая таблица 1С без правила переноса — тест падает (`inventory.test.mjs`);
- **код** (с этапа 1): нет теста `TestT_<узел>` для узла текущего этапа — тест паритета каталога падает (`G4.1`).
